# gantt-task-assignees Specification

## Purpose

Определяет, как на ролевую задачу диаграммы Ганта назначается конкретный исполнитель — автоматически по пулу людей с этой ролью в команде либо вручную с приоритетом над автоматом — и как наличие нескольких исполнителей одной роли позволяет планировщику выполнять их задачи параллельно, а не одной последовательной цепочкой.

## Requirements

### Requirement: Ролевая задача имеет исполнителя

Каждая листовая (ролевая) задача диаграммы Ганта SHALL иметь исполнителя — участника команды, у которого есть роль этой задачи. Исполнитель SHALL определяться системой автоматически при пересчёте расписания команды и SHALL быть доступен в ответе на запрос задач команды вместе с признаком того, назначен он автоматически или закреплён вручную.

Кандидатами на роль SHALL считаться участники, входящие одновременно и в команду эпика, и в число носителей этой роли. Участник, имеющий несколько ролей, SHALL быть кандидатом по каждой из них.

#### Scenario: Задача получает исполнителя при генерации

- **WHEN** для эпика команды генерируются задачи Ганта и в команде есть хотя бы один участник с ролью этой задачи
- **THEN** у каждой ролевой задачи в ответе на запрос задач команды указан исполнитель и признак автоматического назначения

#### Scenario: Участник с несколькими ролями

- **WHEN** участник команды имеет две роли, по обеим из которых у эпика есть оценки
- **THEN** он рассматривается как кандидат на задачи обеих ролей

### Requirement: Задачи одной роли выполняются параллельно разными исполнителями

Планировщик SHALL считать единицей занятости исполнителя, а не роль: две задачи одной и той же роли, назначенные разным исполнителям, SHALL иметь возможность пересекаться по датам. Две задачи, назначенные одному исполнителю, SHALL NOT пересекаться по датам.

Порядок назначения SHALL NOT определять порядок дат: задача, назначенная исполнителю позже, MAY располагаться раньше ранее назначенной, если она целиком помещается в оставшийся свободным промежуток его календаря (см. `gantt-schedule-backfill`). Обязательным остаётся только непересечение.

Зависимости внутри стори SHALL сохраняться без изменений: задача роли из более поздней группы порядка ролей по-прежнему не начинается раньше окончания всех задач предыдущей группы в той же стори.

#### Scenario: Две стори с задачами одной роли и два исполнителя

- **WHEN** у команды есть две стори с задачами одной роли и в команде два участника с этой ролью, оба свободны
- **THEN** задачи назначены разным участникам и выполняются параллельно (пересекаются по датам), а суммарный срок закрытия обеих стори меньше, чем при последовательном выполнении

#### Scenario: Исполнителей меньше, чем задач

- **WHEN** у команды три стори с задачами одной роли, а участник с этой ролью один
- **THEN** все три задачи назначены ему и идут последовательно, не пересекаясь по датам

#### Scenario: Порядок ролей внутри стори сохраняется

- **WHEN** в стори есть задача роли из ранней группы порядка (например, аналитик) и задача роли из поздней группы (например, разработчик), и исполнители у них разные
- **THEN** задача поздней группы всё равно начинается не раньше окончания задачи ранней группы этой же стори

#### Scenario: Назначенная позже задача может стоять раньше

- **WHEN** исполнителю назначена задача более приоритетной стори, начинающаяся нескоро из-за её предусловий, и после этого ему назначается задача менее приоритетной стори, целиком помещающаяся в образовавшийся простой
- **THEN** назначенная позже задача располагается раньше, задачи не пересекаются, а даты более приоритетной задачи не меняются

### Requirement: Автоматическое распределение жадное и детерминированное

При автоматическом назначении система SHALL выбирать из кандидатов роли того, при котором задача начнётся раньше всего с учётом уже занятого времени этого кандидата и ограничений самой задачи. При совпадении получаемой даты старта у нескольких кандидатов система SHALL выбирать их по кругу (round-robin), распределяя такие задачи между кандидатами, а не отдавая их одному.

Автоматическое распределение SHALL быть детерминированным: повторный пересчёт расписания команды при неизменных входных данных SHALL давать то же самое распределение исполнителей. Изменение, не влияющее на входные данные распределения, SHALL NOT приводить к перетасовке исполнителей.

#### Scenario: Повторный пересчёт не меняет исполнителей

- **WHEN** расписание команды пересчитывается повторно без изменения состава команды, порядка эпиков, оценок и закреплений
- **THEN** исполнители всех задач остаются теми же, что и после предыдущего пересчёта

#### Scenario: Равные по дате старта кандидаты получают задачи по кругу

- **WHEN** в начале планирования несколько кандидатов одной роли свободны и любая из нескольких задач может начаться в один и тот же день у любого из них
- **THEN** эти задачи распределяются между кандидатами по кругу, а не назначаются все одному

#### Scenario: Жадный выбор предпочитает раньше освобождающегося

- **WHEN** один кандидат роли занят до более поздней даты, чем другой, и задача может начаться в любой момент
- **THEN** задача назначается тому, кто освобождается раньше

### Requirement: Ручное закрепление исполнителя имеет приоритет

Пользователь с правом редактирования SHALL иметь возможность закрепить за ролевой задачей конкретного исполнителя из числа кандидатов её роли. Закреплённая задача SHALL назначаться указанному человеку при каждом пересчёте расписания, независимо от того, кого выбрал бы автомат.

Приоритет закрепления SHALL распространяться на выбор исполнителя, но не на дату: если закреплённый человек занят, задача SHALL начинаться после его освобождения, даже когда автоматический выбор дал бы более ранний старт. Сдвиг закреплённой задачи SHALL учитываться планировщиком наравне с любым другим — задачи ниже по конвейеру пересчитываются соответственно.

#### Scenario: Закрепление переопределяет автоматический выбор

- **WHEN** пользователь с правом редактирования закрепляет за задачей участника, отличного от назначенного автоматически, и расписание пересчитывается
- **THEN** задача назначена закреплённому участнику и помечена как закреплённая вручную

#### Scenario: Закрепление на занятого человека сдвигает задачу

- **WHEN** задача закрепляется за участником, который занят другими задачами дольше, чем свободный кандидат той же роли
- **THEN** задача назначается закреплённому участнику и её старт сдвигается на дату его освобождения, а зависящие от неё задачи пересчитываются

#### Scenario: Пользователь без права редактирования не может закрепить исполнителя

- **WHEN** пользователь с ролью `member` пытается изменить исполнителя задачи
- **THEN** запрос отклоняется, исполнитель задачи не меняется

### Requirement: Возврат к автоматическому распределению

Пользователь с правом редактирования SHALL иметь возможность снять ручное закрепление и вернуть задачу к автоматическому распределению, выбрав в списке исполнителей пункт «Автоматически» (пустой выбор). После снятия закрепления исполнитель SHALL определяться автоматическим распределением при ближайшем пересчёте расписания.

#### Scenario: Снятие закрепления

- **WHEN** пользователь выбирает для закреплённой задачи пункт «Автоматически»
- **THEN** закрепление снимается, задача получает исполнителя по автоматическому распределению и помечается как назначенная автоматически

### Requirement: Роль без кандидатов планируется как единый ресурс

Если в команде нет ни одного участника с ролью задачи, генерация и пересчёт расписания SHALL выполняться без ошибки. Такая задача SHALL оставаться без исполнителя, а её планирование SHALL вестись по прежним правилам — роль считается единым последовательным ресурсом, и задачи этой роли не пересекаются по датам между собой.

Задачи без исполнителя SHALL быть отличимы на диаграмме от задач с исполнителем.

#### Scenario: Оценка по роли есть, носителей роли в команде нет

- **WHEN** у эпика есть оценка по роли, ни один участник команды которой не имеет
- **THEN** задачи этой роли создаются без исполнителя, генерация завершается успешно, а сами задачи по-прежнему выстроены последовательно друг за другом

#### Scenario: Задачи без исполнителя видны на диаграмме

- **WHEN** в расписании команды есть задачи без исполнителя
- **THEN** на диаграмме они визуально отличимы от задач с исполнителем

### Requirement: Исполнитель начатой или завершённой задачи не переназначается

Задача с ненулевым прогрессом либо с зафиксированной фактической датой завершения SHALL сохранять исполнителя, назначенного ранее, — автоматическое распределение SHALL NOT переназначать её другому человеку. Занятое такой задачей время SHALL учитываться в загрузке её исполнителя при планировании остальных задач.

#### Scenario: Задача в работе не меняет исполнителя

- **WHEN** у задачи выставлен ненулевой прогресс, после чего расписание команды пересчитывается (в том числе при изменении состава команды или порядка эпиков)
- **THEN** исполнитель этой задачи остаётся прежним

#### Scenario: Время начатой задачи занимает календарь исполнителя

- **WHEN** исполнителю назначена задача в работе, и планировщик подбирает исполнителя для следующей задачи той же роли
- **THEN** занятость этого человека начатой задачей учитывается: его следующая задача начинается не раньше следующего рабочего дня после её эффективного окончания

### Requirement: Закрепления и смещения переживают перегенерацию задач

Ручное закрепление исполнителя и ручное смещение старта задачи SHALL сохраняться при перегенерации задач Ганта — как при перегенерации отдельного эпика, так и при массовой перегенерации квартала, — несмотря на то что строки задач при этом удаляются и создаются заново. Восстановление SHALL выполняться по паре «стори (или эпик без стори) + роль».

#### Scenario: Перегенерация квартала сохраняет закрепление

- **WHEN** за задачей закреплён исполнитель, после чего для квартала выполняется массовая перегенерация задач
- **THEN** после перегенерации соответствующая задача снова закреплена за тем же исполнителем

#### Scenario: Перегенерация сохраняет ручное смещение старта

- **WHEN** у задачи выставлено ненулевое ручное смещение старта, после чего задачи её эпика перегенерируются
- **THEN** смещение сохраняется и учитывается в пересчитанном расписании

#### Scenario: Смена оценок не теряет пользовательский ввод

- **WHEN** стори переоценивается, из-за чего меняется длительность её ролевых задач, и задачи эпика перегенерируются
- **THEN** закрепления исполнителей и смещения старта по парам «стори + роль» остаются в силе

### Requirement: Закрепление на выбывшего из пула кандидата

Если закреплённый за задачей человек перестал быть кандидатом её роли (вышел из команды либо лишился роли), система SHALL назначить задачу автоматически, не считая её ошибкой, и SHALL сохранить закрепление, чтобы оно снова вступило в силу, если человек вернётся в пул. Такая задача SHALL быть отличима на диаграмме, чтобы недействующее закрепление не выглядело работающим.

#### Scenario: Закреплённый человек лишился роли

- **WHEN** у участника, закреплённого за задачей, снимается роль этой задачи, и расписание пересчитывается
- **THEN** задача назначается автоматически, а на диаграмме отмечено, что закрепление недействительно

#### Scenario: Закреплённый человек вернулся в пул

- **WHEN** участнику, за которым осталось недействующее закрепление, возвращается роль задачи, и расписание пересчитывается
- **THEN** задача снова назначается ему как закреплённая вручную

### Requirement: Состав команды доступен для выбора исполнителя

Система SHALL предоставлять авторизованному пользователю состав команды с ролями каждого участника через `GET /api/gantt/teams/{id}/members`. Ответ SHALL содержать по каждому участнику идентификатор, имя и полный перечень его ролей — участник с несколькими ролями SHALL возвращаться со всеми ними.

Ошибки SHALL возвращаться в стандартном формате проекта `{ "error": { "code": "...", "message": "..." } }`.

#### Scenario: Запрос состава команды

- **WHEN** авторизованный пользователь запрашивает состав команды, в которую он входит
- **THEN** возвращается список участников с их идентификаторами, именами и всеми их ролями

#### Scenario: Участник с несколькими ролями в ответе

- **WHEN** в команде есть участник с двумя ролями
- **THEN** в ответе у него перечислены обе роли

#### Scenario: Неизвестная команда

- **WHEN** запрашивается состав по несуществующему идентификатору команды
- **THEN** возвращается ошибка в стандартном формате проекта

### Requirement: Исполнитель отображается на диаграмме

Диаграмма Ганта SHALL показывать исполнителя в подписи каждой ролевой задачи. Отображение SHALL сохраняться во всех режимах просмотра (День/Неделя/Месяц), поскольку после появления параллельного выполнения бары одной роли регулярно пересекаются по времени и без имени исполнителя неразличимы.

Модалка деталей задачи SHALL содержать выбор исполнителя со списком кандидатов роли и пунктом «Автоматически», отражающий текущее состояние назначения.

#### Scenario: Подпись задачи содержит исполнителя

- **WHEN** пользователь открывает диаграмму команды, где у задач есть исполнители
- **THEN** в подписи каждой такой задачи виден её исполнитель

#### Scenario: Пересекающиеся задачи одной роли различимы

- **WHEN** на диаграмме две задачи одной роли пересекаются по датам, будучи назначенными разным людям
- **THEN** по подписям видно, какая задача чья

#### Scenario: Модалка отражает состояние назначения

- **WHEN** пользователь открывает модалку деталей ролевой задачи
- **THEN** в выборе исполнителя выбран текущий исполнитель, если он закреплён вручную, либо пункт «Автоматически», если назначение автоматическое
