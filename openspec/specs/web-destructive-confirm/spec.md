# web-destructive-confirm Specification

## Purpose

Задаёт единый способ подтверждения действий, которые необратимо удаляют данные, каскадно затрагивают связанные сущности или снимают права доступа, чтобы такие действия нельзя было выполнить случайным кликом и чтобы пользователь заранее понимал последствия.

## Requirements

### Requirement: Деструктивное действие требует явного подтверждения

Действие, которое необратимо удаляет данные, каскадно удаляет связанные сущности или снимает у пользователя права доступа, SHALL требовать явного подтверждения в отдельном диалоге перед отправкой запроса на сервер. Один клик по кнопке такого действия SHALL не приводить к изменению данных на сервере.

#### Scenario: Снятие администратора команды

- **WHEN** пользователь нажимает кнопку снятия администратора команды
- **THEN** запрос на сервер не отправляется, а показывается диалог подтверждения с указанием, какого пользователя и из какой команды снимают; изменение происходит только после подтверждения

#### Scenario: Отмена подтверждения

- **WHEN** пользователь отменяет диалог подтверждения деструктивного действия
- **THEN** запрос на сервер не отправляется и данные не изменяются

### Requirement: Диалог подтверждения описывает последствия

Диалог подтверждения деструктивного действия SHALL быть выполнен единым для всего интерфейса способом и SHALL называть последствия действия, а не ограничиваться вопросом «вы уверены». Для каскадных удалений диалог SHALL явно перечислять, какие связанные данные будут удалены вместе с выбранной сущностью.

Браузерные диалоги `confirm()` и `alert()` SHALL не использоваться для подтверждения действий и сообщений пользователю.

#### Scenario: Удаление истории

- **WHEN** пользователь инициирует удаление истории
- **THEN** диалог подтверждения явно сообщает, что вместе с историей будут удалены её риски и оценки

#### Scenario: Единообразие диалогов

- **WHEN** пользователь инициирует любое деструктивное действие в интерфейсе — удаление эпика, удаление истории, перегенерацию задач квартала, снятие администратора команды
- **THEN** диалог подтверждения оформлен одинаково по структуре и стилю, а не браузерным окном

#### Scenario: Штатное состояние вместо браузерного оповещения

- **WHEN** пользователь пытается запустить оценку эпика, у которого нет ни одной истории
- **THEN** причина отказа сообщается средствами интерфейса приложения, а не браузерным окном
