## Why

PDF-отчёт о вместимости команды за квартал показывает, **сколько** работы запланировано (матрица ролевых оценок, ёмкость, квоты, риски), но не показывает, **когда** она произойдёт и кто её делает. График есть только на вкладке «Гант» в вебе — то есть в отчёт, который уходит руководству и хранится как артефакт квартала, календарная картина не попадает вовсе.

## What Changes

- **В PDF-отчёт добавляется лист с диаграммой Ганта** — после существующих разделов отчёта, отдельным листом.
- **Состав диаграммы — полное дерево, как на вкладке «Гант»**: эпики, стори и ролевые задачи с исполнителями. Не сокращённая сводка по эпикам.
- **Лист имеет собственный размер, независимый от остального отчёта**: ширина A3 в альбомной ориентации, высота растёт под число строк. Отчёт остаётся ровно одним файлом; лист с диаграммой — один, сколько бы задач ни было, вместо разбиения на несколько.
- **Диаграмма рисуется как SVG на стороне Go** — тем же приёмом, что уже используются диаграммы рисков (`internal/report/svg.go`). Браузерный Frappe Gantt в PDF-конвейере недоступен.
- **Состояния задач переносятся в PDF**: цвет по роли, завершённость, отсутствие исполнителя. Без них диаграмма в отчёте расходилась бы с тем, что пользователь видит в вебе.
- **XLSX-выгрузка не затрагивается** — изменение только в PDF-ветке экспорта.
- Формат ошибок API, схема БД и существующие HTTP-контракты не меняются.

## Capabilities

### New Capabilities
- `pdf-report-gantt-page`: лист с диаграммой Ганта в PDF-отчёте команды за квартал — полное дерево эпиков, сторей и ролевых задач с исполнителями на листе шириной A3 с высотой, растущей под число строк; календарная шкала квартала, состояния задач и поведение при отсутствии задач.

### Modified Capabilities

Требования существующих способностей не меняются. `capacity-report` описывает состав и расчёт данных отчёта (матрица, ёмкость, квоты, округления) — эта заявка ничего в них не меняет, а добавляет отдельный лист поверх. `team-report-export` описывает выгрузку отчёта в PDF/XLSX как таковую и к содержимому листов требований не предъявляет.

## Impact

**Backend** (субагент `backend`):
- `internal/report/svg.go` или новый файл рядом — построитель SVG диаграммы Ганта: дерево строк, календарная шкала, бары по датам, цвет по роли, подписи с исполнителями.
- `internal/report/types.go` — данные задач Ганта в `ReportData`; сейчас их там нет вообще, отчёт собирается из `BuildCapacityReport` плюс риски.
- `internal/report/generator.go` — вторая конвертация в Gotenberg для листа с диаграммой и объединение с основным отчётом; сейчас `GenerateReport` делает одну конвертацию с `PaperSizeA4()` на весь документ.
- `internal/services/` — прокидывание задач Ганта в `GetReportData` (источник — существующий метод сервиса Ганта, возвращающий задачи команды).
- `config/template.html` — при необходимости разметка листа диаграммы; сам шаблон внешний, путь берётся из конфигурации.
- Слои: services → report; transport не затрагивается, новых эндпоинтов нет.

**Frontend**: не затрагивается — кнопка выгрузки отчёта уже существует и её контракт не меняется.

**DevOps**: не затрагивается. Gotenberg 8 уже развёрнут (`docker-compose.yml:44-46`), маршрут объединения PDF входит в его стандартную поставку, новых сервисов и переменных окружения не требуется.

**QA** (субагент `qa`): `internal/report/` — построение SVG на разных наборах задач (пустой, один эпик, полное дерево, задачи без исполнителя), расчёт высоты листа, устойчивость к отсутствию задач Ганта у команды.

Ключевое ограничение реализации: в клиенте Gotenberg размер листа задаётся на **всю конвертацию** (`PaperSize`/`PaperSizeA4` применяются к документу целиком), поэтому лист другого размера внутри того же файла требует либо CSS named pages с `PreferCssPageSize()`, либо отдельной конвертации и объединения через `PDFEngines().Merge()`. Оба метода в подключённой версии клиента доступны; выбор — предмет design.md.
