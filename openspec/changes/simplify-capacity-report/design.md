## Context

См. `proposal.md` — мотивация. Технический контекст:

- Сегодня существуют **два независимых пути расчёта** одних и тех же цифр:
  - `services.BuildCapacityReport` (`internal/services/capacity_report.go`) → `report.CapacityReportResponse` — используется JSON `GET /reports/capacity` (веб-таблица) и XLSX-генератором (`internal/report/xlsx_generator.go`). Уже различает риск-скорректированные (`role_scores`) и сырые (`raw_role_scores`) величины (см. `fix-capacity-report-raw-total`).
  - `epicService.GetReportData` (`internal/services/epic.go:131`) → `report.ReportData`/`EpicReportData` — используется **обоими** потребителями PDF: Telegram-ботом (`internal/telegram/admin_callbacks.go:657`) и веб-эндпоинтом выгрузки (`internal/transport/httpServer/handlers/reports.go:150`, из `add-web-report`). Считает `RoleScores`/`TotalScore` риск-скорректированными (`scaledScore := rs.WeightedAvg * riskFactor`), но подписи в шаблоне (`config/template.html`) называют их «без риска» — оставшийся не обновлённым при `fix-capacity-report-raw-total` путь.
- PDF-шаблон `config/template.html` не версионируется в проде как часть образа — путь конфигурируется через `HTML_TEMPLATE_FILEPATH`/`HTML_TEMPLATE_FILENAME` (см. `.env`, `docker-compose.yml`), но сам файл лежит в репозитории (`config/template.html`) и деплоится как обычный файл конфигурации.
- `report.ReportData` дополнительно содержит данные, которых нет в `CapacityReportResponse`: риски по каждому эпику (`Risks []RiskReportData` — вероятности/влияния/коэффициент) и время генерации (`Generated`), нужные для карточек эпика и SVG-диаграмм (`internal/report/svg.go`).

## Goals / Non-Goals

**Goals:**
- Матрица «эпики × роли» одинаково выглядит и содержит одинаковые числа во всех трёх форматах (веб, PDF, XLSX): только риск-скорректированная трудоёмкость, без пары «Итого/С рисками».
- PDF перестаёт расходиться с web/XLSX по значениям — использует то же ядро агрегации.
- Отображаемые в отчёте суммы всегда равны сумме отображаемых слагаемых (округление вверх на уровне ячейки, суммирование уже округлённых величин).
- Сырые (до риска) оценки остаются доступны вне главной матрицы (JSON `raw_role_scores`, лист «Эпики» в XLSX) для аудита.

**Non-Goals:**
- Не меняем `final_score`/`role_scores` как domain-значения — расчёт квот, статус эпика, всё остальное продолжает использовать точные (неокруглённые) величины.
- Не трогаем формулу расчёта ёмкости (`Capacity`, headcount × 8 × 6 × 0.838) и «Разницу» — округление применяется только к риск-скорректированной трудоёмкости по ролям/эпикам, не к ёмкости.
- Не реализуем в этом изменении сводку по ролям наверх, группировку эпиков по типу или визуальные шкалы (обсуждались как направления A/Б/В) — сознательно отложено, сначала оцениваем эффект от упрощения матрицы.
- Не меняем JSON-контракт `GET /reports/capacity` и параметры/права доступа `GET /reports/export` (`team-report-export` не затрагивается).

## Decisions

### 1. PDF переводится на общее ядро `BuildCapacityReport`, `GetReportData` остаётся тем же интерфейсом
Сигнатура `epicService.GetReportData(ctx, teamID, year, quarter) (*report.ReportData, error)` не меняется — оба вызывающих (`admin_callbacks.go`, `reports.go`) не трогаются. Внутри `GetReportData` вызывает `BuildCapacityReport` для получения ядра (команда/период/ёмкость/квоты/эпики с риск-скорректированными и сырыми ролевыми оценками), затем поверх ядра дозапрашивает риски по каждому эпику (то, что раньше делала отдельная ветка кода) и оборачивает результат в `report.ReportData`. Практически это означает встраивание `report.CapacityReportResponse` в `report.ReportData` (embedding) вместо параллельного пересчёта `RoleScoresMap`/`TotalScore` — поля с одинаковым смыслом продвигаются напрямую, PDF-специфичные (`Risks`, `Generated`) остаются рядом.

Альтернатива — держать `ReportData` полностью отдельным типом и копировать в него нужные поля из `CapacityReportResponse` вручную — отклонена: увеличивает риск повторного расхождения (именно так и появился нынешний баг), тогда как embedding физически не позволяет полям снова разъехаться.

### 2. Шаблон PDF (`config/template.html`) переписывается под новую форму матрицы и корректные подписи
Матрица: одна колонка на роль (риск-скорректированная, округлённая) + одна колонка «Итого (чд)» на эпик — без `TotalScore`/`FinalScore` как двух разных чисел. Карточка эпика: подпись «Сумма оценок (без рисков)» → «Сумма оценок (с учётом риска)» (или аналогичная корректная формулировка), структура карточки (таблица рисков, 3 SVG-чарта) не меняется.

### 3. Алгоритм округления — единый, реализуется дважды (Go и JS), не через новое поле API
Псевдокод (общий для PDF/XLSX-генератора на Go и `renderCapacityTable` на JS):
```
для каждого эпика E, для каждой роли R:
  cell[E][R] = ceil(risk_adjusted_score(E, R))       # округление вверх поячеечно

Итого(E)        = Σ_R cell[E][R]                      # сумма округлённых ячеек строки
Запланировано(R) = Σ_E cell[E][R]                      # сумма округлённых ячеек колонки
Общий итог       = Σ_E Итого(E)                        # сумма округлённых итогов по эпикам
```
`Capacity`/`Diff` по ролям не входят в этот алгоритм — остаются как есть (не риск-скорректированная трудоёмкость, а формула ёмкости).

Реализуется как один helper в пакете `internal/report` (используется и PDF-генератором, и XLSX-генератором — они уже в одном пакете) и один эквивалентный по логике helper в `web/gantt/js/reports-panel.js` для веб-таблицы. JSON-ответ `GET /reports/capacity` остаётся точным (без округления) — округление происходит на стороне каждого из трёх «рендереров», а не в API. Альтернатива (округлять и отдавать готовые целые в самом JSON) отклонена — это ломало бы `raw_role_scores`/аудит-сценарии и требовало бы версионирования контракта.

### 4. Единый источник для label-текста формул
Текстовый блок формул на вкладке «Отчёты» (`web/gantt/index.html`) обновляется вручную вместе с изменением матрицы — как и раньше, синхронизация текста с фактическим расчётом не автоматизирована (см. комментарий в `index.html` про `add-report-formulas-legend`), проверяется вручную/на ревью.

## Risks / Trade-offs

- **[Trade-off] Систематическое завышение «Запланировано»/«Итого» относительно точной суммы** — из-за поячеечного округления вверх (например, три эпика по 0.3 чд по одной роли дадут «Запланировано» = 3, а не `ceil(0.9)` = 1). Это осознанный выбор пользователя (нужны одновременно целые ячейки и сходящиеся суммы) — единственный способ получить оба свойства сразу.
- **[Риск] Расхождение алгоритма округления между Go и JS**, т.к. реализован дважды на разных языках → **Митигация**: точный псевдокод зафиксирован в этом design.md, задача QA — тест на согласованность чисел между PDF/XLSX/веб для одного и того же team_id/year/quarter (см. новое требование «Согласованность данных…» в спеке).
- **[Риск] Регрессия в Telegram-боте**, т.к. `GetReportData` используется и им — рефактор внутренней реализации может незаметно сломать `/report`-команду → **Митигация**: ручная проверка генерации PDF через бота после рефакторинга (задача QA/backend), не только через веб-эндпоинт.
- **[Риск] Скрытые потребители `EpicReportData.TotalScore`/старого «сырого» смысла полей** вне `internal/report`/шаблона — перед рефакторингом проверить usages по всему репозиторию, не только в известных вызывающих местах.

## Migration Plan

Аддитивный/внутренний рефакторинг — миграций БД нет, JSON-контракт не меняется. Раскатывается обычным деплоем (включая обновлённый `config/template.html`, который деплоится как файл конфигурации). Откат — откат образа/коммита; ранее сгенерированные PDF-файлы на диске (если кэшируются) не пересчитываются задним числом, это не проблема, т.к. каждый запрос генерирует файл заново.
