## Context

См. `proposal.md` — Why.

Текущее состояние, важное для подхода:

- `POST /api/tasks/generate` (`internal/transport/httpServer/routers/routers.go:126` → `GanttHandler.GenerateTasks`, `internal/transport/httpServer/handlers/gantt.go:396`) принимает `epic_id` + `start_date` и вызывает `Service.GenerateTasksForEpic` (`internal/gantt/ganttService.go:148`).
- `GenerateTasksForEpic` для одного эпика: удаляет существующие задачи эпика, создаёт parent-задачу эпика → задачи сторей → ролевые задачи, при необходимости присваивает `sort_order`, и в конце **сам вызывает** `RecalculateTeamSchedule(teamID)` — полный пересчёт расписания всей команды.
- `RecalculateTeamSchedule` (`internal/gantt/ganttService.go`) сериализован per-team мьютексом (`teamScheduleLock`, спека `gantt-schedule-recalc-locking`) и является заметно самой дорогой частью операции: он перечитывает и переписывает даты всех задач команды.
- `startDate` в `GenerateTasksForEpic` — не жёсткая дата, а «пол»: она проставляется в placeholder-даты создаваемых строк, после чего конвейерный планировщик раскладывает эпики по `sort_order`.
- `Repository.GetTeamEpicsOrdered(ctx, teamID)` (`internal/gantt/interfaces.go:18`) уже возвращает топ-эпики команды в порядке очереди, со всеми полями `domain.Epic` — включая `Year`, `Quarter`, `Status`, `SortOrder`.
- Фронтенд: панель инструментов вкладки Ганта — один ряд в `web/gantt/index.html` (`.toolbar-left` / `.toolbar-right`), логика генерации — `web/gantt/js/app.js:198` (`generateTasks`). `GET /epics?team_id=...` уже отдаёт `year`, `quarter`, `type` по каждому эпику (используется фильтрами панели скоринга).
- Кастомная модалка подтверждения для необратимых действий в проекте уже сложилась как паттерн — см. `openDeleteEpicModal` (`web/gantt/js/scoring-panel.js:1878`).

## Goals / Non-Goals

**Goals:**
- Один пересчёт расписания команды на всю массовую операцию вместо N пересчётов.
- Переиспользовать существующую логику генерации по эпику без её дублирования и без изменения её контракта.
- Не трогать слой репозиториев и схему БД.
- Фильтрация списка эпиков — на клиенте, без новых query-параметров у `GET /epics`.

**Non-Goals:**
- Фильтрация содержимого самой диаграммы Ганта по периоду (решение пользователя — см. `proposal.md`).
- Асинхронное/фоновое выполнение операции с прогресс-баром: операция синхронная.
- Транзакционность «всё или ничего» по кварталу — частичный успех допустим и отражается в ответе (см. спеку).
- Изменение прав доступа к генерации задач (роль `member` как и раньше не видит эти элементы управления).

## Decisions

### Decision 1: Отдельный эндпоинт `POST /api/tasks/generate-quarter` вместо цикла на фронтенде

**Выбрано**: новый эндпоинт, принимающий `{ team_id, year, quarter, start_date }` и возвращающий `{ message, epics_total, epics_regenerated, epics_failed, tasks_count }`.

**Почему**: цикл `POST /tasks/generate` по каждому эпику из браузера дал бы N полных `RecalculateTeamSchedule` подряд — самая дорогая операция сервиса, к тому же сериализованная per-team мьютексом, то есть запросы выстроились бы в очередь и суммарное время выросло линейно. Плюс между вызовами возможно вклинивание чужих reorder-запросов, из-за чего промежуточные состояния расписания были бы видны другим пользователям.

**Альтернативы**:
- Цикл на фронтенде — отклонён по причинам выше.
- Расширение существующего `/tasks/generate` необязательными полями `year`/`quarter` вместо `epic_id` — отклонено: один эндпоинт с двумя взаимоисключающими режимами хуже читается и ломает простую валидацию текущего контракта.

**Маршрут**: регистрируется в той же аутентифицированной группе, что и `/tasks/generate` (`routers.go`), без дополнительного `RoleAuth` — чтобы права на массовую перегенерацию совпадали с правами на одиночную генерацию (скрытие кнопки для `member` на фронте, как сейчас). Расхождение прав между двумя вариантами одной и той же операции было бы неожиданным для пользователя.

### Decision 2: Новый метод сервиса `GenerateTasksForQuarter` с внутренним «тихим» вариантом генерации

**Выбрано**: в `internal/gantt/ganttService.go` добавляется

```
func (s *Service) GenerateTasksForQuarter(ctx, teamID uuid.UUID, year, quarter int, startDate time.Time) (QuarterGenerationResult, error)
```

Алгоритм:
1. `GetTeamEpicsOrdered(ctx, teamID)` → отфильтровать в памяти по `Year == year && Quarter == quarter && Status == domain.StatusScored`, сохранив порядок очереди.
2. Если подходящих эпиков нет — вернуть результат с нулевыми счётчиками, без вызова пересчёта.
3. Для каждого эпика — общая внутренняя функция создания строк задач (тело текущего `GenerateTasksForEpic` **без** финального `RecalculateTeamSchedule`), ошибка по конкретному эпику логируется и увеличивает `epics_failed`, не прерывая цикл.
4. Один вызов `RecalculateTeamSchedule(ctx, teamID)` в конце — при условии, что хотя бы один эпик обработан успешно.

`GenerateTasksForEpic` остаётся публичным и сохраняет текущее поведение (генерация + пересчёт), становясь тонкой обёрткой над той же внутренней функцией — существующий эндпоинт и его тесты не меняются.

**Почему**: вынесение «создание строк» отдельно от «пересчёт расписания» — минимальное вмешательство, дающее ровно один пересчёт на операцию. Фильтрация в памяти по уже загруженному `GetTeamEpicsOrdered` избавляет от нового метода репозитория и, что важнее, бесплатно сохраняет порядок очереди `sort_order`, от которого зависит раскладка.

**Альтернативы**:
- Новый метод репозитория `GetTeamEpicsByYearQuarterOrdered` — отклонён: `GetTeamEpicsOrdered` уже отдаёт нужные поля, количество топ-эпиков команды заведомо мало, а расширение интерфейса `gantt.Repository` тянет за собой правки моков в тестах без выигрыша.
- Переиспользовать существующий `GetEpicsByTeamYearQuarter` (репозиторий, используется отчётом по capacity) — отклонён: он не входит в интерфейс `gantt.Repository`, а его сортировка не гарантирует порядок очереди планировщика.

### Decision 3: Частичный успех вместо «всё или ничего»

Эпики в статусах `NEW`/`SCORING` отфильтровываются заранее и вообще не участвуют в операции (их задачи не удаляются). Для отобранных `SCORED`-эпиков ошибка генерации отдельного эпика (например, legacy-эпик без оценок ролей) не откатывает уже перегенерированные эпики: она попадает в счётчик `epics_failed` и в лог, операция продолжается.

**Почему**: одна незаскоренная стори не должна блокировать перегенерацию всего квартала — это ровно тот ручной перебор, от которого избавляет фича. Откат по кварталу потребовал бы единой БД-транзакции через все вызовы репозитория и заметно более сложного контракта сервиса.

**Trade-off**: пользователь может получить квартал, перегенерированный частично. Смягчение — счётчики в ответе и явная сводка в уведомлении на фронтенде.

### Decision 4: Фильтрация списка эпиков — на клиенте

Год/квартал фильтруют `#epic-select` из уже загруженного `state.get('epics')` (ответ `GET /epics?team_id=...`, содержащий `year`/`quarter`). Список годов строится динамически из годов эпиков команды, к нему всегда добавляется текущий год.

**Почему**: тот же подход, что уже принят для фильтров панели скоринга (change `add-epic-list-filters`) — единообразие и никаких новых серверных параметров. Число эпиков команды мало, фильтрация в памяти незаметна.

**Альтернатива**: серверные query-параметры `?year=&quarter=` у `GET /epics` — отклонены как избыточные при текущих объёмах данных.

### Decision 5: Кастомная модалка подтверждения, не `window.confirm`

Подтверждение массовой перегенерации реализуется кастомной модалкой по образцу `openDeleteEpicModal` (`web/gantt/js/scoring-panel.js:1878`) — с явным указанием периода (год, квартал) и даты начала в тексте.

**Почему**: операция необратима (задачи всех эпиков квартала удаляются и создаются заново, вместе с фактическими данными прогресса, которые не переживают пересоздание строк), а в проекте для таких действий уже принята кастомная модалка. `window.confirm` не позволяет оформить текст и не соответствует дизайн-системе.

### Decision 6: Раскладка панели инструментов в два ряда

`.toolbar-left` вкладки Ганта разбивается на два ряда (`flex-direction: column` у контейнера, каждый ряд — `flex` со своим `gap`): 1-й ряд — год, квартал, дата; 2-й ряд — выбор эпика, «Сгенерировать задачи», «Перегенерировать квартал», «Порядок эпиков», «Порядок историй». Блок `.toolbar-right` (режимы отображения, счётчик задач) не меняется. Стили — в существующие файлы `web/gantt/css/components.css` / `responsive.css`, без новых css-файлов.

## Risks / Trade-offs

- **Долгий синхронный запрос при большом квартале** (много эпиков × генерация + один пересчёт) → операция всё равно дешевле, чем N пересчётов; на время запроса кнопка блокируется и показывает состояние загрузки, чтобы исключить повторный клик.
- **Потеря фактических данных по перегенерированным эпикам** (`Progress`, `ActualEndDate`, `ActualEffortDays` пересозданных задач) — прямое следствие семантики «перегенерировать заново», такая же, как у существующей одиночной генерации → смягчается явным предупреждением в модалке подтверждения.
- **Конкурентный запрос другого пользователя во время операции** → per-team мьютекс `RecalculateTeamSchedule` уже гарантирует, что итоговое расписание согласовано (спека `gantt-schedule-recalc-locking`); новых требований к блокировкам не вводится.
- **Частичный успех выглядит как полный, если не смотреть на текст уведомления** → в уведомлении явно указываются количество перегенерированных и, при наличии, количество неуспешных эпиков.
- **Расхождение фильтра списка эпиков и области действия кнопки квартала** (в списке — все эпики периода, в перегенерации — только `SCORED`) → в модалке подтверждения указывается, что перегенерируются только заскоренные эпики периода.

## Migration Plan

Миграций БД и изменений конфигурации нет. Изменение обратно совместимо: существующий `POST /tasks/generate` и его поведение сохраняются, новый эндпоинт — аддитивный. Откат — обычный откат образа на предыдущий тег (`release.yml`), состояния в БД, требующего отдельного отката, не создаётся.
