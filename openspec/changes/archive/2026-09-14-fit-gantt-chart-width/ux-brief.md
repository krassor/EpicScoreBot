# UX-постановка для фронтенда (задача 1.1)

Составлена субагентом `ux` (код не пишет). Реализуется задачами 2.1–2.6.

## 1. Верхняя граница растягивания — потолка нет

Не вводить верхний предел `column_width`.

Обоснование: Frappe Gantt масштабирует сетку и бары пропорционально одной и той
же величине — растягивание колонки не искажает соотношение бара к его датам (это
гарантировано спекой: «бар SHALL по-прежнему начинаться и заканчиваться на датах
своей задачи»). Широкая колонка в масштабе «День» при малом числе задач — это не
искажение данных, а более крупный масштаб отображения; читаемость дат не
деградирует. Требование спеки «свободного места справа SHALL NOT оставаться»
исключений не допускает, поэтому потолок означал бы закладывать пустое поле
вопреки уже принятой спеке.

**Требует решения пользователя.** `ux` подчёркивает, что это продуктовый
компромисс (читаемость на редких широких экранах против буквального соответствия
безусловному SHALL), а не техническая деталь, и оставляет выбор за
пользователем/архитектором.

Критерий приёмки: `column_width` вычисляется как
`max(штатная ширина режима, доступная ширина / число колонок)` без верхнего
клампа при любом сочетании масштаба, размера окна и числа задач.

## 2. Подписи баров — переход между состояниями не трогаем, контраст усиливаем

Логика «вынести подпись за пределы бара, если не помещается» — внутренняя
механика библиотеки (`.bar-label.big`), её не переопределять. Переход между
«внутри бара» и «снаружи» источником дёрганья не является: обе CSS-вариации
используют близкие светлые заливки (`#ffffff` и `--text-primary` `#f0f0ff`),
скачка яркости нет, а сам переход дискретен (в момент пересчёта, не анимация).

**Что менять — контраст подписи внутри цветного бара.** Сейчас он ниже WCAG AA
почти для всех шести ролевых цветов; единственная защита — `drop-shadow`, который
в контраст по WCAG не засчитывается. Расчёт `ux` для белого текста на заливках
ролей: IT-лидер `#8b5cf6` → 4.23:1, Аналитик `#3b82f6` → 3.68:1, BE `#10b981` →
2.54:1, FE `#f59e0b` → 2.15:1, Mobile `#ec4899` → 3.53:1, QA `#6366f1` → 4.46:1 —
все ниже требуемых 4.5:1. Сегодня это отчасти маскируется тем, что длинные
подписи не влезают в узкий бар и уходят в `.bar-label.big` на тёмный фон страницы
(контраст >15:1). Растягивание делает бары шире, поэтому доля подписей внутри
цветного бара вырастет — это прямое следствие темы задачи, а не отдельный баг.

Цвета ролей (`--color-role-*`) не трогать — они используются в легенде, бейджах и
админ-панели за пределами Ганта. Вместо этого в `web/gantt/css/gantt.css:118-128`
заменить `filter: drop-shadow(...)` на SVG-обводку текста токеном фона:

```css
.gantt .bar-label {
    fill: #ffffff !important;
    font-weight: 600;
    paint-order: stroke;
    stroke: var(--bg-primary);
    stroke-width: 3px;
    stroke-linejoin: round;
}

.gantt .bar-label.big {
    fill: var(--text-primary) !important;
    paint-order: stroke;
    stroke: var(--bg-primary);
    stroke-width: 3px;
    stroke-linejoin: round;
}
```

`--bg-primary` — существующий токен (`variables.css:5`), новых цветов не вводится.
`.gantt-epic .bar-label` / `.gantt-story .bar-label` (`gantt.css:139-142, 152-155`)
не трогать — там только `font-size`/`font-weight`, правило контраста наследуется.

Критерий приёмки: подпись любого ролевого бара, помещающаяся внутри бара после
растягивания, читаема — глиф визуально отделён от заливки тёмной обводкой при
любом из шести ролевых цветов; переход `.bar-label` ↔ `.bar-label.big` не даёт
заметного скачка яркости.

## 3. Узкие экраны — поведение не меняется

На ширинах, где доступная ширина меньше `штатная_ширина × число_колонок`, формула
`max(...)` естественно возвращает штатную ширину: растягивание не включается,
горизонтальная прокрутка внутри `.app-gantt-wrapper` (`overflow: auto`, уже
задано) сохраняется. Новых правил в `responsive.css` не требуется — это следствие
формулы, а не отдельная адаптивная ветка.

Уточнение к обработчику resize: ширину контейнера читать **в момент срабатывания**
debounced-колбэка (`getBoundingClientRect().width` на актуальном DOM), а не из
заранее вычисленного значения. Иначе на мобильном клиенте временное изменение
viewport (доводка safe-area при повороте, анимация системной клавиатуры Telegram)
может спровоцировать пересчёт по устаревшей ширине.

Критерий приёмки: на разрешениях ≤480px и ≤768px колонка любого масштаба не уже
штатной; `.app-gantt-wrapper` — единственный прокручиваемый по горизонтали
контейнер, страница целиком вбок не скроллится.

## 4. Индикация нештатного масштаба — не нужна

Не добавлять пометок «сетка растянута» / «ширина колонки нештатная». Заголовки
колонок с реальными датами остаются системой отсчёта независимо от ширины —
пользователь ориентируется по датам, а не по пиксельной ширине ячейки, а
переключатель День/Неделя/Месяц уже сообщает выбранный масштаб. Ширина колонки —
деталь рендера, а не настройка, которой пользователь управляет, поэтому индикация
была бы шумом без привязанного к ней действия.

Критерий приёмки: в задачах 2.1–2.6 не появляется новых элементов UI (бейджей,
тултипов, подписей), сообщающих о факте растягивания.

## 5. Поведение при resize — дискретный пересчёт без анимации

- **Без анимации.** Пересчёт после гашения дребезга применяется одномоментно
  через `update_options`. Не добавлять CSS-transition на `.bar`,
  `.gantt-container` или ширину SVG: Frappe Gantt перерисовывает бары
  императивно (ставит атрибуты `x`/`width` напрямую), CSS-переход плавной
  интерполяции не даст, а лишние транзишны на пересчитываемых элементах создают
  риск дополнительных reflow во время серии resize-событий.
- **Без вспышки узкой сетки на первом рендере.** Двухшаговый первый рендер
  (построить со штатной шириной → узнать фактическое число колонок → применить
  вычисленную) выполнять синхронно в одном такте JS, без `await`/`setTimeout`
  между шагами — иначе пользователь на долю секунды увидит нерастянутую сетку.
  Проверить в ветке полной пересборки `renderGantt()`.
- **Позиция прокрутки при смене ширины.** При resize, меняющем `column_width`,
  сохранять не абсолютный `scrollLeft`, а относительную позицию:
  `scrollLeft / scrollWidth` до пересчёта → то же отношение после. Причина:
  при изменении ширины колонки меняется масштаб «пикселей на день», и абсолютный
  `scrollLeft` физически указывает уже на другую дату — визуально диаграмма
  «дёргается», хотя пользователь прокрутку не трогал. Эффект заметен в узком
  коридоре размеров (колонка растянута, но диапазон всё ещё шире окна). Это не
  требование спеки: если сохранение абсолютного `scrollLeft` заметно проще —
  допустимо, но зафиксировать как принятый компромисс.

Критерий приёмки: разворачивание и сужение окна растягивает или возвращает сетку
к штатной ширине без анимации-растяжения и без вспышки узкого рендера на первой
отрисовке; перетаскивание края окна не вызывает заметного подвисания; прокрутка
не сбрасывается в 0 при пересчёте.

## Не трогать

- Расчёт дат, состав задач, конвейерный планировщик, `on_date_change` /
  `on_progress_change` / reorder-логику.
- Высоту бара и строки — вертикальная подгонка исключена как non-goal design.md.
- `--color-role-*` и легенду — контраст чинится локально в правилах `.bar-label`.
- Существующие id и обработчики `.btn-view`, `#gantt-chart`, `#app-gantt-wrapper`.

## Ограничение ревью

Живого браузерного ревью не проводилось: `claude-in-chrome` недоступен, запуск
приложения требует Docker/PostgreSQL/Telegram-авторизации. Выводы получены чтением
кода и спецификаций плюс ручным расчётом контраста по формуле WCAG — значения
контраста стоит перепроверить инструментом при реализации.
