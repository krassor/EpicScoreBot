## Context

См. proposal.md — Why. Технические факты:

- `loadEpicData()` (`web/gantt/js/scoring-panel.js:374`) — единая точка перезагрузки данных панели деталей, вызывается минимум из 12 мест файла после любого действия, потенциально меняющего состояние эпика/стори (голосование, переопределение оценок, массовое голосование по роли, создание/удаление стори и т.д.).
- Текущая логика выбора стори внутри неё:
  ```js
  currentStories = (await apiGet(`/epics/${selectedEpic.id}/stories`)...) || [];
  if (currentStories.length > 0) {
      if (!selectedStory || !currentStories.some(s => s.id === selectedStory.id)) {
          selectedStory = currentStories[0];
      }
      // ... дальше используется selectedStory, который мог остаться старой ссылкой
  }
  ```
  `some()` только проверяет присутствие id в свежем списке и не подменяет саму переменную — если сторя с тем же id всё ещё существует (обычный случай), `selectedStory` остаётся прежним JS-объектом со старыми полями (`status`, `final_score`, `evaluating_role_ids`, ...), хотя `currentStories` уже содержит свежую версию этой же стори.
- Дальнейший рендер (`renderDetails()` → `renderRoleScoresTableHtml(roleScores, story, isAdmin)` и другие места) читает поля именно из `selectedStory`, а не ищет свежую версию в `currentStories` — поэтому визуально «не замечает» изменение статуса, пока `selectedStory` не будет переприсвоен (это происходит только при полной перезагрузке страницы, когда `selectedStory` стартует как `null`).
- Похожая проблема потенциально не затрагивает `selectedEpic` в этом же файле: он обновляется отдельной функцией `refreshAfterAdminEdit()` (строки ~414-431), которая явно ищет и переприсваивает `selectedEpic = fresh` из заново загруженного списка эпиков. Эта функция уже служит прецедентом верного паттерна для устранения того же класса проблемы на уровне эпика — но `loadEpicData()` вызывается сама по себе гораздо чаще и не проходит через `refreshAfterAdminEdit()`.

## Goals / Non-Goals

**Goals:**
- Гарантировать, что после `loadEpicData()` переменная `selectedStory` (если её id всё ещё присутствует в списке) всегда указывает на объект, только что полученный с сервера, а не на устаревшую ссылку.
- Исправить проблему в одном месте (`loadEpicData()`), не трогая 12 мест вызова.

**Non-Goals:**
- Обновление `selectedEpic` внутри самой `loadEpicData()` — это уже решается отдельно через `refreshAfterAdminEdit()` там, где это нужно (админские действия над оценками), и не является предметом этого бага.
- Изменение backend/API — проблема чисто фронтенд, в клиентском кешировании состояния.
- Общий рефакторинг паттерна «повторная загрузка + выбор элемента» на другие сущности (эпики в списке, риски и т.д.) — вне обнаруженного репорта, делать по отдельному запросу при необходимости.

## Decisions

1. **Точечный фикс внутри `loadEpicData()`**: заменить `if (!selectedStory || !currentStories.some(...)) selectedStory = currentStories[0]` на поиск свежего объекта по id и безусловное переприсваивание, если он найден:
   ```js
   const freshSelectedStory = selectedStory
       ? currentStories.find(s => s.id === selectedStory.id)
       : null;
   selectedStory = freshSelectedStory || currentStories[0];
   ```
   Альтернатива — точечно мутировать существующий объект (`Object.assign(selectedStory, fresh)`) вместо переприсваивания ссылки: отклонена, т.к. переприсваивание проще, не создаёt риска рассинхронизации, если где-то в другом месте файла держится собственная ссылка на старый объект `selectedStory`, и уже является используемым в проекте паттерном (`refreshAfterAdminEdit`, `selectEpic` присваивают напрямую).
2. **Не трогать существующее поведение при отсутствии/исчезновении стори**: если `selectedStory` не задан или сторя с таким id больше не существует в списке (удалена), поведение не меняется — выбирается `currentStories[0]`, как и раньше.
3. **Фикс делается в общей функции, а не только для сценария «Оценить всей ролью»**: см. proposal.md — так покрываются все ~12 мест вызова `loadEpicData()`, включая личные голоса и переопределения оценок, без необходимости чинить каждое место отдельно (решение согласовано с пользователем).

## Risks / Trade-offs

- **[Риск] Регрессия для других 11 мест вызова `loadEpicData()`**, которые не были явно протестированы под этот баг → Митигация: фикс минимальный и по смыслу строго корректнее прежнего поведения (всегда даёт актуальные данные вместо иногда устаревших); QA-задача должна прогнать сквозные сценарии для нескольких разных вызывающих действий (не только массовое голосование по роли), см. tasks.md.
- **[Trade-off] Не покрывается аналогичная потенциальная проблема с `selectedEpic` внутри `loadEpicData()`** (если эпик меняет статус без прохождения через `refreshAfterAdminEdit()`) → осознанно вне рамок (Non-Goals); при обнаружении отдельного репорта потребуется отдельный change.

## Migration Plan

Не требуется — чисто клиентское исправление одной функции, без изменений API/схемы БД. Деплой — обычная выкатка фронтенда. Откат — стандартный revert коммита.
