## Context

См. `proposal.md` — мотивация и итоги расследования. Технический контекст:

- `Service` (`internal/gantt/ganttService.go:35`) — `struct { repo Repository; log *slog.Logger }`, никакого состояния синхронизации сейчас нет.
- `RecalculateTeamSchedule(ctx, teamID)` вызывается из `ReorderEpic`, `ReorderStory`, а также (не проверено явно в этом расследовании, но по аналогии) вероятно из других мест, меняющих `progress`/структуру задач команды — нужно найти ВСЕ точки вызова при реализации, не только эти две.
- Приложение деплоится одним контейнером бэкенда (`docker-compose.yml`, `app-backend-service-epic-score-bot` — один сервис, без реплик/масштабирования) — см. `devops.md`. Это определяет выбор механизма блокировки (Decision 1).
- Go 1.26, `internal/gantt` уже использует `context.Context` во всех сигнатурах репозитория — блокировка должна уважать отмену контекста (не блокироваться вечно, если клиент отменил запрос).

## Goals / Non-Goals

**Goals:**
- Гарантировать, что `RecalculateTeamSchedule` для одной команды не выполняется двумя горутинами одновременно.
- Не задерживать пересчёты РАЗНЫХ команд друг относительно друга.
- Не вносить новых зависимостей, не менять `Repository`-интерфейс.

**Non-Goals:**
- Не решаем задачу горизontального масштабирования бэкенда (несколько инстансов/реплик) — при текущей однорепличной архитектуре in-process блокировки достаточно; переход на блокировку уровня БД (Postgres advisory lock) — будущая работа, если архитектура деплоя изменится.
- Не переписываем сам алгоритм `recalculateEpicSchedule` — расследование подтвердило, что он корректен при изолированном вызове.
- Не мигрируем/не чиним руками уже накопленные на проде некорректные даты — самоисправляются следующим чистым пересчётом (см. proposal.md).

## Decisions

### 1. In-process per-team мьютекс, не блокировка на уровне БД
Два варианта рассматривались:

**A. In-process `sync.Mutex` per team ID** (выбрано):
```go
type Service struct {
    repo Repository
    log  *slog.Logger

    scheduleMu sync.Map // teamID (uuid.UUID) -> *sync.Mutex
}

func (s *Service) teamScheduleLock(teamID uuid.UUID) *sync.Mutex {
    v, _ := s.scheduleMu.LoadOrStore(teamID, &sync.Mutex{})
    return v.(*sync.Mutex)
}
```
`RecalculateTeamSchedule` в начале делает `lock := s.teamScheduleLock(teamID); lock.Lock(); defer lock.Unlock()`. Просто, без новых зависимостей, без изменения `Repository`. Ограничение: работает только в пределах одного процесса — при нескольких репликах бэкенда за балансировщиком не защитит.

**B. Postgres advisory lock** (`pg_advisory_xact_lock(hashtext(teamID))`), отклонено для этой итерации:
Требует нового метода в `Repository`-интерфейсе (например `WithTeamLock(ctx, teamID, fn func(ctx) error) error`), доступа к транзакции на уровне репозитория (сейчас `RecalculateTeamSchedule` делает отдельные вызовы репозитория без общей транзакции — обернуть всё в одну транзакцию само по себе более инвазивное изменение). Корректно работает при любом числе реплик бэкенда. Отклонено сейчас, т.к. деплой — один контейнер (Non-Goals), а сложность/риск изменения заметно выше.

Если в будущем появится нужда в нескольких репликах — заменить content реализацию `teamScheduleLock`/точку вызова на advisory lock, не меняя сигнатуру `RecalculateTeamSchedule` и вызывающий код.

### 2. Блокировка — вокруг всего тела `RecalculateTeamSchedule`, не вокруг отдельных операций
Блокировка берётся в начале функции и держится до её завершения (успешного или с ошибкой, через `defer Unlock()`) — то есть на всё время чтения `GetTeamEpicsOrdered`, всех `GetGanttTasksByEpicID`, и всех `UpdateGanttTaskDates`/`UpdateGanttTaskProgress` вызовов внутри. Это самый простой способ гарантировать, что конкурентный вызов видит либо полностью ДО, либо полностью ПОСЛЕ предыдущего пересчёта — никогда середину.

Alternative — блокировать только точку записи (каждый `UpdateGanttTaskDates` по отдельности) — отклонено: не решает проблему, т.к. промежуточные ЧТЕНИЯ (`roleFreeAt`, `teamFloor`) всё равно могли бы происходить на "перемешанных" данных между отдельными короткими блокировками записи.

### 3. Найти и защитить ВСЕ вызывающие места, не только Reorder*
Нужно явно перечислить (при реализации, через `grep -rn "RecalculateTeamSchedule"`) каждое место, откуда вызывается `RecalculateTeamSchedule`, и убедиться, что блокировка находится ВНУТРИ самой функции `RecalculateTeamSchedule` (а не в каждом вызывающем месте по отдельности) — так гарантируется защита независимо от того, сколько сейчас (и в будущем) точек входа.

### 4. Логирование для верификации гипотезы
Добавить `s.log.Debug`/`Info` с teamID в начале и конце `RecalculateTeamSchedule`, и отдельную запись, если `lock.Lock()` фактически ждал (не смог захватить сразу) — например через `TryLock()` сначала, и если не удалось — залогировать "waiting for schedule lock" перед блокирующим `Lock()`. Это даст прод-логи, подтверждающие или опровергающие, что конкуренция реально происходит — если после деплоя проблема не повторяется, но и логов ожидания нет, это будет значить, что гипотеза была неверна и причина в другом.

## Risks / Trade-offs

- **[Риск] Гипотеза может не подтвердиться** — если проблема повторится и после деплоя блокировки, значит, причина в чём-то другом (например, в самих данных — устаревшие/нигде не переписанные gantt_tasks.sort_order с прошлых частичных сохранений, до фикса `fix-epic-reorder-stale-cache`). Логирование (Decision 4) должно дать понять, была ли вообще конкуренция для конкретного инцидента, если он повторится.
- **[Trade-off] In-process блокировка не защищает при масштабировании бэкенда на несколько реплик** — осознанно принято, см. Non-Goals; задокументировано для будущего пересмотра.
- **[Риск] `sync.Map` растёт бессрочно** (по одной записи на каждый когда-либо встреченный teamID) — в масштабах этого проекта (число команд ограничено, не тысячи) это не проблема на практике; отдельно не чиним (не вводим TTL/очистку) в рамках этого change.

## Migration Plan

Аддитивно, без миграций БД, без изменения API-контрактов. После деплоя: выполнить один reorder (например, пересохранить текущий порядок эпиков через модалку) для команды, где наблюдался баг — по описанному в proposal.md механизму самокоррекции это должно поправить уже некорректные даты. Отдельная задача в tasks.md — не код, ручная проверка после деплоя.
