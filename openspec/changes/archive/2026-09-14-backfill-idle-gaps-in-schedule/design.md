## Context

Мотивация — см. proposal.md «Why». Здесь только то, что формирует подход.

Текущая ресурсная модель планировщика (`internal/gantt/ganttService.go`):

```go
type scheduleState struct {
    pools          map[uuid.UUID][]domain.User // roleID -> кандидаты, отсортированы по uuid
    assignments    map[assignmentKey]domain.TaskAssignment
    assigneeFreeAt map[uuid.UUID]time.Time     // userID -> «занят до»
    rrCursor       map[uuid.UUID]int
    roleFreeAt     map[uuid.UUID]time.Time     // roleID -> то же, для ролей с пустым пулом
}
```

Дата старта листовой задачи считается как `moveToWorkDay(maxTime(target, nextAvailable(freeAt), epicFloor))`, где `target = groupPrevEnd + offset`. Запись в календарь — `advanceFreeAt`, которая двигает отметку только вперёд.

Факты, определяющие решение:

- **Обход строго приоритетный**: эпики по `epics.sort_order`, стори внутри эпика, группы ролей внутри стори по `defaultRoleOrder`. Вся стори размещается до начала следующей. Значит всё, что уже лежит в календаре, не менее приоритетно, чем то, что размещается сейчас.
- **`epicFloor` сегодня равен `teamFloor`** — самой ранней плановой дате старта родительских баров эпиков команды (`ganttService.go:531`), которая, в свою очередь, приходит из поля «Дата начала» в тулбаре при генерации. Это не «сегодня».
- **`RecalculateTeamSchedule(ctx, teamID)` принимает только команду** и вызывается из девяти мест: генерация эпика, перегенерация квартала, оба реордера, изменение прогресса, смена исполнителя, смещение старта. Состояние тулбара до большинства из них не доходит.
- **Замороженные задачи** (`Progress > 0` или `ActualEndDate != nil`) даты не пересчитывают, но своим эффективным окончанием двигают календарь исполнителя.
- **Пересчёт запускается очень часто** и полностью переписывает даты, поэтому обязан быть идемпотентным при неизменном входе; детерминизм уже обеспечен сортировкой пула по `uuid` и пересозданием `rrCursor` на каждый вызов.

## Goals / Non-Goals

**Goals:**

- Перестать терять простои, не меняя ни порядок приоритета, ни уже размещённые даты.
- Сохранить детерминизм: тот же вход — то же расписание.
- Сохранить вырождение в текущее поведение там, где промежутков нет.

**Non-Goals:**

- Дробление задачи между промежутками и сокращение длительности ради помещения — решение пользователя, зафиксировано в спеке.
- Перемещение уже размещённых задач ради уплотнения (полноценная оптимизация makespan). Задача NP-трудна, и предсказуемость по-прежнему важнее плотности.
- Изменение политики выбора исполнителя: жадный `argmin` с round-robin на равенстве остаётся.
- Изменение смысла приоритета: обход остаётся приоритетным, меняется только способность видеть промежутки.
- Учёт переключения контекста между стори как стоимости.

## Decisions

### Решение 1. Ватерлиния заменяется интервальным календарём

`assigneeFreeAt map[uuid.UUID]time.Time` и `roleFreeAt` превращаются в календари занятых интервалов: `map[uuid.UUID][]interval`, где интервалы упорядочены и не пересекаются. `advanceFreeAt` превращается в резервирование интервала.

*Почему не оставить ватерлинию и добавить рядом список «дырок»:* две структуры описывали бы одно и то же состояние, и их пришлось бы синхронизировать при каждой записи. Интервалы — единственный источник истины, дырки выводятся из них.

*Почему интервалы, а не битовая карта рабочих дней:* горизонт планирования — кварталы, а число задач на человека измеряется десятками. Список интервалов меньше, не требует выбора гранулярности и естественно ложится на уже существующие `moveToWorkDay`/`nextAvailable`.

*Что остаётся неизменным:* сами карты по-прежнему живут внутри одного вызова `RecalculateTeamSchedule` и пересоздаются на каждый вызов — семантика «команда планируется автономно» и per-team блокировка не затрагиваются.

### Решение 2. Поиск самого раннего подходящего промежутка (first-fit)

Дата старта задачи длительностью `d` для исполнителя `u`:

```
earliest = max(target, floor)
t = минимальное t ≥ earliest, при котором [t, t+d] целиком лежит
    в свободном интервале календаря u
если такого t нет → t = после последней брони u   // прежнее поведение
```

*Почему first-fit, а не best-fit* (самый тесный подходящий промежуток): пользователь сформулировал правило как «раньше берём менее приоритетную задачу, если она умещается», то есть приоритет отдаётся ранней дате, а не плотности упаковки. Best-fit экономил бы крупные промежутки для крупных задач, но давал бы менее раннее расписание и был бы труднее объясним: непонятно, почему задача не заняла доступный ранний промежуток.

*Почему поиск даёт детерминизм:* календарь строится в детерминированном порядке обхода, интервалы упорядочены, «минимальное подходящее `t`» однозначно. Ни одна ветка не зависит от порядка обхода `map`.

*Следствие для выбора исполнителя:* функция `start(u)`, по которой считается `argmin`, просто начинает искать промежуток вместо сравнения с ватерлинией. Сам жадный выбор и round-robin тай-брейк не меняются.

### Решение 3. Граница `floor` — новая настройка команды, а не состояние интерфейса

```
настройка выключена (по умолчанию) → floor = teamFloor
настройка включена                 → floor = max(teamFloor, today)
```

Граница применяется ко **всему** размещению: `earliest = max(target, floor)`, поэтому при включённой настройке раньше текущей даты не планируется ни одна задача, а не только засыпаемая.

*Почему граница общая, а не только для поиска промежутка:* варианты различаются ровно в одной ветке — когда подходящего промежутка нет и задача встаёт после последней брони. «Хвост» после последней брони — это не промежуток, а открытый интервал, и отдельная нижняя граница для него потребовала бы двух разных пределов внутри одного поиска. Поведение «при включённой настройке ничего не планируется в прошлом» проще объяснить пользователю, чем «дырки в прошлом закрыты, но задача после брони, кончившейся вчера, встанет сегодня минус один день».

Настройка хранится у команды и читается внутри `RecalculateTeamSchedule` — там же и тем же приёмом, что уже читаются пулы исполнителей и закрепления: пачкой на команду, вне цикла по задачам.

*Почему не параметр запроса и не состояние тулбара:* пересчёт вызывается из девяти мест, и до большинства из них состояние интерфейса не доходит. Настройка-параметр означала бы, что смысл расписания зависит от того, каким действием его пересчитали: сгенерировали с запретом — промежутки в прошлом закрыты, затем кто-то изменил процент выполнения — пересчёт прошёл без запрета, и они открылись. Молча. Спека поэтому требует, чтобы настройка действовала при любом пересчёте.

*Почему по умолчанию выключено:* выключенное значение воспроизводит сегодняшнюю границу, поэтому выкатка не переставляет существующие расписания сама по себе — меняется только то, где засыпка реально нашла промежуток.

*Почему на команду, а не на квартал:* пересчёт и так ведётся на команду целиком, календари исполнителей общие для всех её кварталов. Настройка на квартал потребовала бы разной границы внутри одного прохода и разошлась бы с моделью.

### Решение 4. Замороженные задачи резервируют фактический интервал

Задача с ненулевым прогрессом или зафиксированной фактической датой завершения резервирует в календаре свой реальный интервал `[start, эффективное окончание]`, а не двигает ватерлинию.

*Следствие, о котором нужно знать:* это делает доступным промежуток **перед** начатой задачей. При включённой настройке он обычно отсекается границей «сегодня» — начатая задача стартовала в прошлом. При выключенной ещё не начатая задача может встать раньше уже начатой. Пользователь принял это, выбрав механизм отсечки по дате вместо отдельного правила для замороженных задач.

*Почему не запрещать промежуток перед замороженной задачей отдельным правилом:* это добавило бы второе, независимое понятие границы поверх уже выбранного и усложнило бы объяснение расписания без нового поведения — граница по дате закрывает тот же случай.

### Решение 5. Правило распространяется на роли без исполнителей

Календарь роли (`roleFreeAt`) получает ту же интервальную модель и тот же поиск промежутка.

*Почему:* иначе поведение расходилось бы без причины, видимой пользователю: две одинаковые по смыслу задачи планировались бы по-разному в зависимости от того, укомплектована роль в команде или нет. Непересечение задач роли между собой при этом сохраняется — оно следует из той же интервальной модели.

## Risks / Trade-offs

**Расписание становится чувствительнее к изменениям длительностей** → удлинение одной задачи может лишить промежуток вместимости и перестроить цепочку засыпок, поэтому даты будут «дышать» между пересчётами заметнее, чем при ватерлинии. Смягчения нет, это цена плотности; стоит предупредить пользователей, а не пытаться стабилизировать искусственно.

**Менее приоритетная стори может финишировать раньше более приоритетной** → принято сознательно: пользователь выбрал засыпку простоя, явно предпочтя её сохранению «приоритет = порядок завершения».

**Переключение контекста между стори не учитывается** → в модели засыпка бесплатна, в жизни исполнитель прыгает между стори. При коротких задачах это может оказаться дороже простоя. Предохранительный клапан — ручное закрепление исполнителя, уже существующее.

**Ошибка в резервировании интервала даёт пересекающиеся задачи одного человека** — регрессия, которую на диаграмме легко не заметить, потому что параллельные бары одной роли теперь штатны → отдельный тест на непересечение по каждому исполнителю, а не только на ожидаемые даты.

**Промежутки в прошлом при выключенной настройке** → сохраняется сегодняшнее положение дел: расписание и сейчас может содержать прошедшие даты, если `teamFloor` в прошлом. Заявка это не чинит и не усугубляет — при выключенной настройке граница совпадает с прежней.

**Рост стоимости пересчёта** → поиск промежутка линеен по числу интервалов исполнителя, число задач на человека измеряется десятками, поэтому на практике незаметен. Отдельно следить не требуется.

## Migration Plan

1. Миграция под настройку команды применяется автоматически существующим механизмом `internal/migrator` при старте контейнера.
2. Значение по умолчанию выключено, поэтому сразу после выкатки граница поиска совпадает с прежней. Изменения в расписаниях появятся только там, где засыпка нашла промежуток — и только после ближайшего пересчёта (генерация, реордер, изменение прогресса).
3. **Откат:** схема после миграции обратно совместима — колонка настройки просто не читается предыдущей версией кода, поэтому возврат образа на предыдущий тег работает без вмешательства в БД. Расписания при этом вернутся к прежнему виду при первом же пересчёте.
