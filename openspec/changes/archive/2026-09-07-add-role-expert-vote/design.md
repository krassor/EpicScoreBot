## Context

См. proposal.md - Why. Технический контекст (изучен напрямую):

- Завершение скоринга (`Service.TryCompleteEpicScoring`, `internal/scoring/scoring.go:176-276`) сравнивает ГЛОБАЛЬНЫЙ (не по ролям) `GetSubmittedEpicScorersCount` с `GetExpectedScorersCount` (`internal/repositories/scoring.go:358-414`) — оба через `COUNT(DISTINCT user_id)` по всем оцениваемым ролям эпика сразу. Разбивки "сколько из ожидаемых участников роли X уже проголосовали" в репозитории не существует.
- `epic_role_scores` (используется существующей таблицей «Оценки по ролям» через `GET /epics/{id}/role-scores`) заполняется ТОЛЬКО внутри `TryCompleteEpicScoring`, и только когда все ожидаемые голоса уже собраны — то есть во время активного `SCORING` эта таблица для эпика всегда пуста.
- `Repository.CreateEpicScore` (`internal/repositories/scoring.go:12-22`) — upsert по ключу `(epic_id, user_id)`, безопасно вызывать повторно для одного и того же пользователя.
- `Repository.GetUsersByTeamIDAndRoleID(ctx, teamID, roleID) ([]domain.User, error)` (`internal/repositories/user.go:79-106`) — уже существует, возвращает участников команды с конкретной ролью.
- `TryCompleteEpicScoring` уже вызывается синхронно после каждого `CreateEpicScore` в четырёх местах (веб для участника, веб для админа-за-участника, два места в Telegram) — при добавлении нового пути вызова (массовое голосование) нужно так же вызвать её один раз в конце.

## Goals / Non-Goals

**Goals:**
- Переиспользовать существующий механизм голосования (`epic_scores` + `TryCompleteEpicScoring`) без изменения логики подсчёта ожидаемых/поданных голосов — риск регрессии в уже работающей и недавно отлаженной логике завершения скоринга (см. `add-schedule-recalc-locking`, где нашли реальную гонку данных в соседней части системы) сведён к минимуму.
- Один клик администратора = N обычных голосов (по одному на каждого участника роли), просто выполненных одним действием.

**Non-Goals:**
- Не вводим разбивку подсчёта ожидаемых/поданных голосов по ролям — это отдельная, более рискованная переработка `GetExpectedScorersCount`/`GetSubmittedEpicScorersCount`/`TryCompleteEpicScoring`, не нужная для решения задачи пользователя при выбранном подходе (массовое голосование).
- Не трогаем оценку рисков — она остаётся отдельным, независимым условием завершения скоринга (`risk.Status == StatusScored` для всех рисков), как и раньше.
- Не различаем в `epic_scores` "экспертно проставленный" голос от голоса, который участник ввёл сам — после массового проставления голос участника неотличим от того, как если бы он ввёл то же число лично через `AdminSubmitEpicScore` (уже существующий, принятый в проекте паттерн "админ голосует за участника").
- Не добавляем аналог этой фичи для статуса `NEW` (до запуска скоринга) — по формулировке задачи используется явно статус `SCORING`.

## Decisions

**1. Новый метод `Service.SubmitExpertRoleScore(ctx, epicID, roleID uuid.UUID, score int) (scoredCount int, err error)` в `internal/scoring/scoring.go`.**
Требует `epic.Status == domain.StatusScoring` (новая проверка; иначе — новая типизированная ошибка `ErrScoringAlreadyComplete`/переиспользуем существующий паттерн ошибок пакета). Загружает `repo.GetUsersByTeamIDAndRoleID(ctx, epic.TeamID, roleID)`; если список пуст — возвращает ошибку "нет участников с этой ролью в команде". Для каждого участника — `repo.CreateEpicScore(ctx, epicID, user.ID, roleID, score)`. После цикла — один раз `s.TryCompleteEpicScoring(ctx, epicID)`. Возвращает количество затронутых участников (для ответа API/UI).
Альтернатива (отклонена): ввести отдельное понятие "роль оценена экспертно" с флагом в `epic_evaluation_roles` и разбивкой подсчёта голосов по ролям в `TryCompleteEpicScoring`. Отклонена как избыточно рискованная для решаемой задачи (см. Non-Goals) — massовое голосование даёт тот же результат для пользователя, переиспользуя уже проверенный код.

**2. Новый хендлер `AdminSubmitExpertRoleScore` (`POST /admin/scores/role/expert`) в `admin_scores.go`, новый роут в существующей admin-only группе.**
Права доступа и team-scoping — копия уже существующего паттерна (`AdminOverrideRoleScore`/`AdminOverrideFinalScore`): session → superadmin или `IsTeamAdminOfAny` → точечная проверка `IsTeamAdminOf` по team эпика. Путь намеренно отличается от уже существующего `POST /admin/scores/role` (это переопределение уже вычисленного значения, доступно только при `SCORED`) — разные механизмы, разные предусловия, смешивать в одном эндпоинте нельзя.
Тело запроса: `{epic_id, role_id, score}`. Ответ: `{"status":"ok","epic_id":...,"role_id":...,"scored_count":N,"epic_status":"SCORING"|"SCORED"}` (актуальный статус эпика после возможного авто-завершения — фронтенду не нужно гадать, произошёл переход в SCORED или нет, по отдельному запросу).

**3. Frontend: во время `SCORING` таблица «Оценки по ролям» строится из `evaluating_role_ids` эпика, а не из `GET /epics/{id}/role-scores`.**
Пока эпик в статусе `SCORING`, эндпоинт `role-scores` всегда возвращает пустой список (см. Context) — существующий источник данных таблицы не подходит. Вместо этого при `SCORING` таблица берёт список ролей из уже загруженного объекта эпика (`evaluating_role_ids`) и сопоставляет имена ролей через уже существующий на этой же странице справочник ролей (используемый формой редактирования эпика для чекбоксов ролей) — новый эндпоинт получения имён ролей не нужен. При `SCORED` таблица продолжает работать как раньше (источник — `role-scores`), новая кнопка экспертного голосования не показывается — вместо неё, как и раньше, показывается уже существующая кнопка переопределения.
Кнопка «Оценить всей ролью» показывается только при `SCORING` и только администратору. По клику — модалка подтверждения (текст: "оценка перезапишет личные голоса участников этой роли, если они есть") → `apiPost('/admin/scores/role/expert', {epic_id, role_id, score})` → обновление данных панели (`loadEpicData()`, как и после других изменяющих скоринг действий на этой странице).

## Risks / Trade-offs

- [Риск] Массовая перезапись личных голосов необратима и не логируется отдельно от обычного голоса → Митигация: обязательное подтверждение перед действием (см. Decisions п.3); это тот же уровень аудита, что и у уже принятого в проекте паттерна "админ голосует за участника".
- [Риск] Если между вызовом `GetUsersByTeamIDAndRoleID` и завершением цикла состав участников команды изменится (кто-то добавлен/удалён из команды или роли одновременно другим администратором) — возможна гонка (аналогично уже известной и исправленной гонке пересчёта расписания, `add-schedule-recalc-locking`). Риск низкий (состав участников команды меняется редко и не параллельно массово), в рамках этого change отдельная блокировка не вводится — при необходимости будет отдельный change по образцу уже реализованного паттерна team-scoped `sync.Mutex`.
