## Context

См. proposal.md — Why/What Changes. Технические факты, важные для реализации:

- `Repository.DeleteEpic` (`internal/repositories/epic.go:320`) уже реализован как `DELETE FROM epics WHERE id = $1`. Все дочерние таблицы (`stories`/`epics.parent_epic_id`, `epic_role_scores`, `risks`, `role_evaluations` и т.д.) объявлены с `REFERENCES epics(id) ON DELETE CASCADE` (см. `internal/migrator/migrations/001_initial.sql`, `006_quarterly_planning.sql`, `007_stories.sql`) — каскадное удаление гарантирует БД, дополнительный код в репозитории не нужен.
- `GanttHandler.DeleteEpic` (`internal/transport/httpServer/handlers/admin.go:782`) уже написан и помечен комментарием «SuperAdmin only», но читает параметр как `chi.URLParam(r, "id")` и **не зарегистрирован** ни в одной группе `routers.go`.
- В `routers.go` уже есть группа только для `superadmin`:
  ```go
  mux.Group(func(mux chi.Router) {
      mux.Use(myMiddleware.RoleAuth(r.ganttHandler.Repo(), r.ganttHandler.Repo(), r.ganttHandler.Config(), "superadmin"))
      mux.Get("/admin/team-admins", ...)
      ...
  })
  ```
  Новый маршрут удаления эпика логично добавить сюда же.
- В том же роутере уже зарегистрирован `mux.Put("/epics/{epic_id}", r.ganttHandler.UpdateEpic)` внутри группы `admin`. chi требует одинакового имени параметра для одного и того же места в дереве маршрутов независимо от HTTP-метода — значит новый `DELETE /epics/{epic_id}` обязан использовать то же имя параметра `epic_id`, а не `id`, иначе при старте приложения chi запаникует на конфликте параметров пути.
- Готового переиспользуемого confirm-модального окна во фронтенде нет. Есть только `showErrorModal` (`web/gantt/js/utils.js`) под одну задачу (сообщение об ошибке) и набор разовых модалок редактирования в `scoring-panel.js` (`openEditEpicModal`, `openEditStoryModal`, `openEditRiskModal`) — все построены по одному паттерну (`.modal-overlay` + `.modal-content` внутри `<div class="modal hidden">`, переключение классов `hidden`/`display: flex`).
- Кнопка «Редактировать» уже условно рендерится по `isAdmin` в `renderDetails()` (`scoring-panel.js:290,306`). Для кнопки удаления понадобится отдельный флаг `isSuperAdmin`, т.к. право уже сейчас — только `superadmin` (см. proposal.md).
- После удаления самого выбранного эпика паттерн сброса состояния уже есть — `clearDetails()` (`scoring-panel.js:200`) очищает `#scoring-details` и `selectedEpic`; `loadScoringEpics(teamId)` (`scoring-panel.js:145`) перезагружает список эпиков команды.

## Goals / Non-Goals

**Goals:**
- Подключить уже написанный `DeleteEpic` к роутеру с правильной защитой доступа (`superadmin`).
- Дать superadmin кнопку удаления эпика с явным модальным подтверждением, без использования нативного `window.confirm`.
- Корректно обновить UI (список эпиков + панель деталей) после удаления.

**Non-Goals:**
- Мягкое удаление (soft delete) / архивация эпика — не рассматривается, удаление остаётся жёстким (как уже реализовано в `Repository.DeleteEpic`).
- Ограничение удаления по статусу эпика (например, запрет для `SCORING`/`SCORED`) — по решению пользователя такие ограничения не вводятся.
- Изменение формата HTTP-ошибок API — используется существующий стандарт проекта без изменений.
- Уведомление участников команды об удалении эпика (Telegram-нотификации) — не требуется.

## Decisions

1. **Маршрут и защита**: `DELETE /api/gantt/epics/{epic_id}` регистрируется в уже существующей `superadmin`-группе `routers.go` (там же, где `/admin/team-admins`). Alternative: завести отдельную группу — избыточно, т.к. группа с middleware `RoleAuth(..., "superadmin")` уже есть и по смыслу подходит (деструктивные операции над сущностями).
2. **Переименование параметра пути**: в `DeleteEpic` заменить `chi.URLParam(r, "id")` на `chi.URLParam(r, "epic_id")` — единственный способ избежать конфликта параметров пути chi с уже существующим `PUT /epics/{epic_id}` на том же узле дерева маршрутов. Это точечное изменение сигнатуры чтения параметра, поведение хендлера не меняется.
3. **Кастомная модалка подтверждения вместо `window.confirm`**: пользователь явно просил модальное окно подтверждения (не нативный confirm, который уже используется для удаления истории). Модалка верстается по существующему паттерну `.modal-overlay`/`.modal-content` (как `openEditEpicModal`), а не через новую переиспользуемую утилиту в `utils.js` — в кодовой базе нет прецедента общей confirm-утилиты, и заводить абстракцию ради одного места использования избыточно (см. правило проекта не проектировать под гипотетические будущие нужды).
4. **Видимость кнопки — `isSuperAdmin`, а не `isAdmin`**: соответствует ограничению доступа на бэкенде (шаг 1). Флаг вычисляется рядом с существующими `isAdmin`/`isLeaderOrAdmin` в `renderDetails()`.
5. **Без проверки статуса эпика ни на фронте, ни на бэке**: соответствует явному решению пользователя разрешить удаление в любом статусе; `Repository.DeleteEpic` уже не делает такую проверку — менять её не нужно.

## Risks / Trade-offs

- **[Риск] Безвозвратная потеря реальных оценок участников** при удалении эпика в статусе `SCORING`/`SCORED` → Митигация: явный текст предупреждения в модальном окне подтверждения о каскадном удалении историй/рисков/оценок; решение сознательно принято пользователем как приемлемое для этой роли (только `superadmin`).
- **[Риск] Конфликт параметров маршрута chi** (`id` vs `epic_id`) при регистрации нового маршрута без переименования → Митигация: переименование параметра — часть задачи (см. Decision 2), backend-агент должен внести это изменение до регистрации маршрута.
- **[Trade-off] Дублирование верстки модалки** вместо общей утилиты подтверждения → осознанно принято ради простоты; если в будущем понадобится третья confirm-модалка, стоит вынести общий хелпер отдельным рефакторингом (не в рамках этого change).

## Migration Plan

Не требуется — правки backend (роутинг + переименование параметра) и frontend (кнопка + модалка) выкатываются одним релизом, миграций схемы БД не требуется (используется уже существующая схема с каскадными FK). Откат — стандартный откат деплоя (revert коммита), данных в БД правки не меняют.
