## Context

Мотивация — см. proposal.md «Why». Здесь только то, что формирует подход.

Текущий PDF-конвейер (`report.Generator.GenerateReport`, `internal/report/generator.go:200-266`):

```
ReportData → buildReportTemplateData → html/template (config/template.html)
           → Gotenberg Chromium ConvertHTML().PaperSizeA4().Margins(1,1,1,1)
           → файл на диске, путь возвращается наружу
```

Факты, которые определяют решение (сверены по коду и по исходникам подключённого клиента `github.com/nativebpm/gotenberg@v1.1.1`, а не по документации):

- **Размер листа задаётся на всю конвертацию.** `PaperSize(width, height)`, `PaperSizeA4()`, `Landscape()` — параметры запроса целиком, не отдельной страницы. Внутри одной конвертации разные листы разного размера штатно не получаются.
- **Есть два обхода, оба доступны в клиенте**: `PreferCssPageSize()` (размер берётся из CSS `@page`) и `PDFEngines().Merge()` (объединение нескольких PDF в один). Gotenberg 8 развёрнут в `docker-compose.yml:44-46`, оба маршрута входят в его стандартную поставку.
- **SVG-диаграммы в отчёте уже строятся на Go**: `BuildRiskProbabilityDiagram`, `BuildRiskImpactDiagram`, `BuildRiskCoefficientDiagram` (`internal/report/svg.go`) возвращают строку SVG, которая кладётся в шаблон как `template.HTML`. Готовый приём, который переиспользуется.
- **Данных Ганта в `ReportData` нет вообще.** Она собирается из `CapacityReportResponse` (общее ядро с JSON `/reports/capacity` и XLSX) плюс риски по эпикам. Задачи с датами, ролями и исполнителями надо прокидывать отдельно.
- **Шаблон отчёта внешний** — `config/template.html`, путь из `PdfConfig.HtmlTemplateFilePath/Name`, монтируется в контейнер. Правки шаблона — это правки развёрнутого файла, а не только кода.
- **Отчёт вызывается из двух мест** — HTTP `ExportTeamReport` (`handlers/reports.go:150`) и Telegram-бот (`telegram/admin_callbacks.go:657`), оба через `GetReportData` + `GenerateReport`. Изменение сигнатур затрагивает обе точки.

## Goals / Non-Goals

**Goals:**

- Лист с диаграммой собственного размера внутри одного файла, без деградации остальных разделов отчёта.
- Устойчивость выгрузки: проблемы с данными Ганта не должны валить отчёт целиком.
- Переиспользовать существующий приём «SVG на Go + `template.HTML`», а не вводить второй способ рисования графики.

**Non-Goals:**

- Интерактивность (ссылки, всплывающие подсказки, слои PDF).
- Совпадение с вебом пиксель в пиксель. Совпадать обязаны состав, порядок и даты (спека), а не оформление: в вебе рисует Frappe Gantt, в отчёте — собственный SVG.
- Перенос в отчёт всех состояний вкладки «Гант». Спека называет три (роль, завершённость, отсутствие исполнителя); недействующее закрепление, факт-маркеры «раньше/позже плана» и стрелки зависимостей в объём не входят.
- Настройка размера листа и состава диаграммы пользователем.
- Изменение XLSX-выгрузки.

## Decisions

### Решение 1. Отдельная конвертация листа диаграммы и объединение через `PDFEngines().Merge()`

Отчёт собирается двумя запросами к Gotenberg: основная часть — как сегодня, `PaperSizeA4()`; лист диаграммы — отдельный HTML с `PaperSize(ширина, высота)`, вычисленными в Go. Затем оба PDF объединяются `PDFEngines().Merge()` в один файл, который и возвращается наружу.

*Почему не `PreferCssPageSize()` с CSS named pages* (`@page gantt { size: ... }` + `page: gantt`): именованные страницы — относительно свежая возможность Chromium, и её поведение зависит от версии внутри образа `gotenberg/gotenberg:latest`. Тег `latest` в `docker-compose.yml` означает, что версия может смениться при любом пересборе, и вместе с ней — размер листа в отчёте. Кроме того, `PreferCssPageSize()` переключает на CSS-управление размером **весь** документ, то есть основную часть отчёта пришлось бы тоже перевести на `@page`-правила и заново проверить её вёрстку. Ради одного добавленного листа это неоправданный риск для того, что уже работает.

*Почему не отдельный файл рядом с отчётом:* спека требует один файл — точка выгрузки, имя и тип не меняются.

*Цена решения:* два обращения к Gotenberg вместо одного плюс третье на объединение. Отчёт формируется по явному действию пользователя, а не в горячем пути, поэтому приемлемо; тайм-аут (сейчас 60 секунд на клиенте и на контексте) нужно пересмотреть с учётом трёх запросов вместо одного.

### Решение 2. Высота листа вычисляется в Go до конвертации

Высота листа = отступы + шапка со шкалой + число строк × высота строки, где высота строки фиксирована и подобрана читаемой. Ширина — постоянная, соответствующая A3 в альбомной ориентации.

*Почему считать в Go, а не отдать браузеру:* размер листа передаётся параметром запроса (Решение 1), то есть должен быть известен **до** конвертации. Узнать фактическую высоту отрендеренного содержимого можно было бы только из самого браузера, что вернуло бы нас к CSS-управлению размером со всеми его рисками.

*Следствие:* высота SVG и высота листа считаются из одной величины — числа строк, — поэтому обязаны считаться в одном месте по одной формуле. Расхождение даст либо обрезанную снизу диаграмму, либо пустое поле.

*Почему высота строки фиксирована, а не подгоняется:* спека прямо запрещает уменьшать строки ниже читаемого размера ради фиксированной высоты. Фиксированная высота строки плюс растущий лист — прямая реализация этого требования; подгонка строки под лист была бы реализацией противоположного.

### Решение 3. Диаграмма — SVG, построенный на Go, тем же приёмом, что диаграммы рисков

Строится строка SVG и кладётся в шаблон как `template.HTML`, как уже сделано для трёх диаграмм рисков (`svg.go`).

*Почему не отрисовка в вебе со снятием скриншота* (у Gotenberg есть `ScreenshotHTML`): потребовало бы поднимать вкладку «Гант» с авторизованной сессией внутри конвейера отчёта, тянуть Frappe Gantt с CDN в момент генерации и зависеть от доступности CDN. Растровая картинка вдобавок хуже печатается и не масштабируется.

*Почему не переиспользовать Frappe Gantt на сервере:* это браузерная библиотека, работающая с DOM; в Go-процессе её нет.

*Цена:* второй, независимый рендерер диаграммы. Расхождение с вебом по оформлению неизбежно и принято в Non-Goals; спека фиксирует обязательным совпадение состава, порядка и дат — их и надо проверять.

### Решение 4. Задачи Ганта прокидываются в `ReportData` как отдельное поле

`ReportData` получает поле с задачами команды за период — рядом с `Risks` и `Generated`, то есть тем же способом, каким PDF уже добавляет то, чего нет в общем ядре агрегации. Источник — существующий метод сервиса Ганта, возвращающий задачи команды; заполнение — в `GetReportData`.

*Почему не в `CapacityReportResponse`:* это общее ядро с JSON-эндпоинтом `/reports/capacity` и XLSX-выгрузкой. Добавление туда задач Ганта изменило бы формат уже отдаваемого JSON и потянуло бы данные, которые ни JSON, ни XLSX не нужны. Комментарий в `types.go` фиксирует это разделение прямо.

*Почему не отдельный аргумент `GenerateReport`:* обе точки вызова (HTTP и Telegram) уже передают `ReportData` целиком; расширение структуры не меняет их сигнатуры, а дополнительный аргумент менял бы.

### Решение 5. Сбой данных Ганта деградирует лист, а не отчёт

Ошибка получения задач или построения диаграммы SHALL приводить к отчёту без листа диаграммы, с записью в журнал, а не к ошибке выгрузки (спека, «Отсутствие задач не ломает отчёт»).

*Почему:* отчёт о вместимости самоценен и сегодня формируется без всякого Ганта. Отказ выдавать его целиком из-за проблемы с добавленным листом — регрессия для существующей функциональности.

*Тот же путь для пустых данных:* команда без сгенерированных задач — не ошибка, а штатное состояние начала квартала.

### Решение 6. Кодирование состояний не опирается только на цвет

Роль, завершённость и отсутствие исполнителя различаются признаком, сохраняющимся при чёрно-белой печати (штриховка, контур, помётка), а не только заливкой. Лист несёт легенду.

*Почему это отдельное решение, а не деталь:* в вебе роль кодируется исключительно цветом заливки, и прямой перенос этой схемы в печатный документ дал бы шесть неразличимых оттенков серого. Отчёт — печатный артефакт, и это меняет требования к кодированию.

## Risks / Trade-offs

**Три запроса к Gotenberg вместо одного увеличивают время выгрузки и число точек отказа** → выгрузка запускается вручную и не находится в горячем пути; тайм-ауты пересматриваются под новый конвейер; сбой ветки диаграммы деградирует лист, а не отчёт (Решение 5).

**Расхождение вычисленной высоты листа с фактической высотой SVG** даёт обрезанную диаграмму или пустое поле → обе величины выводятся из одного числа строк по одной формуле в одном месте (Решение 2); проверяется тестом на нескольких размерах набора задач.

**Второй рендерер диаграммы расходится с вебом при развитии** — новые состояния появляются на вкладке «Гант» и не появляются в отчёте → принято осознанно (Non-Goals); спека фиксирует обязательный минимум (состав, порядок, даты, три состояния), расхождение оформления допустимо.

**Очень большая команда даёт лист экстремальной высоты**, который неудобно печатать → прямое следствие выбранного пользователем поведения «увеличивать лист по высоте» вместо разбиения на листы; альтернативы (сжатие до нечитаемого, разбиение) были рассмотрены и отклонены.

**Правка `config/template.html` — это правка внешнего файла**, монтируемого в контейнер → менять его надо согласованно с выкаткой образа, иначе старый шаблон встретится с новым кодом; при отдельной конвертации листа (Решение 1) разметка листа может жить в собственном шаблоне и не трогать существующий.

**Тег `gotenberg/gotenberg:latest` в docker-compose** означает, что версия конвертера может смениться при пересборе → Решение 1 выбрано в том числе потому, что не завязано на версионно-зависимую поддержку CSS named pages; `PaperSize` и `Merge` — стабильная часть API Gotenberg 8.

## Migration Plan

Схема БД, API и формат выгрузки не меняются — отдельных шагов не требуется. Откат — возврат образа на предыдущий тег; если разметка листа вынесена в собственный шаблон (Решение 1), существующий `config/template.html` остаётся нетронутым, и откат не требует его восстановления.
