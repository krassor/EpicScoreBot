## Context

См. `proposal.md` — мотивация и скриншот бага. Технический контекст:

- `epicTemplateData` (`internal/report/generator.go`) встраивает `EpicReportData`, которая, в свою очередь, встраивает `EpicReportItem` (`internal/report/types.go`) — у него уже есть оба поля: `RoleScores map[string]float64` (риск-скорректированные) и `RawRoleScores map[string]float64` (сырые, без риск-фактора). Оба заполняются в `services.BuildCapacityReport` (общее ядро агрегации, см. `simplify-capacity-report`, решение 1) и одинаково доступны PDF через embedding.
- `config/template.html`, секция карточки эпика (строки ~285-310): `{{range $role, $score := .RoleScores}}` — читает риск-скорректированную карту, хотя `.RawRoleScores` того же типа лежит рядом на той же структуре и ничего не мешает читать её вместо этого.
- Строка суммы под таблицей ролей сейчас жёстко печатает `{{printf "%.2f" .FinalScore}}` (не сумму отображённых выше строк) — то есть даже если бы `RoleScores` были правильными, сумма всё равно не была бы суммой видимых строк, а была бы отдельным (в данном случае — тем же) числом `FinalScore`.
- Шапка карточки (`Итого: {{printf "%.0f" .FinalScore}}`) и низ карточки (`Итоговая оценка с учётом рисков: {{printf "%.0f" .FinalScore}}`) уже используют `FinalScore` — они корректны и не меняются.
- `config/template.html` не в git (см. `simplify-capacity-report`, design.md) — после реализации нужен ручной перенос на сервер, отдельная задача не в компетенции этого change.

## Goals / Non-Goals

**Goals:**
- Карточка эпика в PDF показывает подлинную сырую трудоёмкость по ролям и её сумму — независимую от риск-скорректированного итога, видимого в шапке/низу той же карточки.
- Сумма строки «без рисков» вычисляется из тех же значений, что показаны в таблице выше (а не берётся из не связанного с ними `FinalScore`).

**Non-Goals:**
- Не меняем главную матрицу «эпики × роли» в начале PDF (`RoundedRoleScores`/`RoundedTotal`, колонка «Итого с рисками (чд)») — она уже верно показывает риск-скорректированные значения по `simplify-capacity-report` и этим изменением не затрагивается.
- Не меняем веб-интерфейс и XLSX-выгрузку — у них нет аналога детальной карточки эпика с разбивкой по ролям.
- Не вводим округление для этой секции (человеко-дни/поячеечный ceil из `simplify-capacity-report` — про капасити-планирование; карточка эпика — это детализация скоринга, отдельный контекст) — сохраняется текущий формат `%.2f`.
- Не трогаем таблицу рисков, SVG-диаграммы, легенду рисков — эта часть карточки уже корректна и не касается raw/risk-adjusted различия.

## Decisions

### 1. Источник данных для таблицы ролей — `RawRoleScores`, без новых полей на уровне ядра агрегации
`EpicReportItem.RawRoleScores` уже содержит нужные значения (см. Context) — используем их напрямую в шаблоне (`{{range $role, $score := .RawRoleScores}}`), никаких изменений в `services.BuildCapacityReport` не требуется.

### 2. Новое поле `RawTotalScore` в `epicTemplateData`, вычисляется в `buildReportTemplateData`
Шаблон не умеет суммировать значения map в `html/template` без вспомогательной функции — поэтому сумма считается в Go, рядом с уже существующим вычислением `RoundedTotal` (для главной матрицы), по аналогии:
```go
var rawTotal float64
for _, v := range e.RawRoleScores {
    rawTotal += v
}
```
Добавляется как `RawTotalScore float64` в `epicTemplateData` (`internal/report/generator.go`), заполняется в цикле `buildReportTemplateData`, который уже строит `epics []epicTemplateData`.

### 3. Правки в шаблоне ограничены секцией «Оценки по ролям» карточки эпика
```html
{{range $role, $score := .RawRoleScores}}
<tr><td>{{$role}}</td><td>{{printf "%.2f" $score}}</td></tr>
{{end}}
<tr class="total-row">
  <td>Сумма оценок (без рисков)</td>
  <td>{{printf "%.2f" .RawTotalScore}}</td>
</tr>
```
Шапка (`Итого: {{.FinalScore}}`) и низ карточки (`Итоговая оценка с учётом рисков: {{.FinalScore}}`) — без изменений.

### 4. Обновление существующего теста `TestTemplateHTML_RendersWithoutError`
Текущие ассерты `strings.Contains(html, "без рисков")` (ожидает false) и `strings.Contains(html, "с учётом риска")` (ожидает true) были написаны под предыдущую (неверную) версию правки и требуют инверсии первой проверки:
- `strings.Contains(html, "без рисков")` теперь SHALL быть `true` (подпись возвращается, уже с верным смыслом)
- `strings.Contains(html, "с учётом риска")` остаётся `true` (низ карточки не менялся)
- Добавить fixture с риск-фактором ≠ 1 (например, `RawRoleScores` суммарно 100, `FinalScore` 60) и проверить, что в HTML присутствует и «100.00» (сумма без рисков), и «60» (итог) — то есть числа реально разные, не только текстовые подписи.

## Risks / Trade-offs

- **[Риск] Регрессия читаемости, если риск-фактор близок к 1** — сумма «без рисков» и «Итого» будут почти совпадать, что может вновь создать впечатление дублирования. Это ожидаемое и корректное поведение (см. спеку, сценарий «риск-фактор равен 1»), не требует отдельной мitigation — раз значения реально независимы, совпадение при риск-факторе 1 корректно.
- **[Уже известно] `config/template.html` не деплоится автоматически** — то же напоминание, что и в `simplify-capacity-report`: после реализации нужен ручной перенос файла на сервер.
