## Context

См. `proposal.md` — «Why». Технический контекст: `GetCapacityReport` (`internal/transport/httpServer/handlers/reports.go:46-`) для каждого эпика считает `riskFactor = FinalScore / baseScore` и кладёт в `EpicReportItem.RoleScores` уже умноженные на этот фактор значения (`reports.go:177-178` для эпиков со сторями, `reports.go:207-208` для эпиков без сторей). Те же риск-скорректированные значения агрегируются в `rolePlanned` (`reports.go:179, 209`) и уходят в `RoleCapacityData.Planned`, откуда фронтенд (`web/gantt/js/reports-panel.js`) строит строки «Запланировано (трудоемкость)», «Доступно (ёмкость)», «Разница».

Пользователь подтвердил: сводные строки по ролям команды (`Запланировано`/`Доступно`/`Разница`) должны и дальше учитывать риск-буфер — они не меняются. Меняется только то, как трудоёмкость эпика показывается в его собственной строке таблицы (колонки по ролям + «Итого»).

## Goals / Non-Goals

**Goals:**
- Колонки по ролям и «Итого (чд)» в строке конкретного эпика показывают сырую трудоёмкость (без риск-фактора эпика/историй).
- «С рисками (чд)» продолжает показывать `final_score` без изменений.
- `role_capacities[].planned` и производные от них строки таблицы (`Запланировано`/`Доступно`/`Разница`) остаются риск-скорректированными — без изменений в расчёте.
- Обратная совместимость API: существующие поля `role_scores` и `final_score` не меняют смысл и не удаляются.

**Non-Goals:**
- Не меняется формула риск-фактора и алгоритм скоринга.
- Не меняется поведение сводных ролевых строк (`Запланировано`/`Доступно`/`Разница`).
- Не меняется отчёт по квотам (feature/tech, `quotas`).

## Decisions

**Новое поле `raw_role_scores` в `EpicReportItem`.** Backend добавляет `RawRoleScores map[string]float64 \`json:"raw_role_scores"\`` — сумма `rs.WeightedAvg` по ролям без умножения на `riskFactor`/`storyRiskFactor` (для эпиков со сторями — по каждой оценённой стори без её риск-фактора). Существующее поле `role_scores` не трогаем: оно остаётся риск-скорректированным и продолжает питать `rolePlanned`/`role_capacities[].planned` — без изменений в этой части кода.

Альтернатива (отклонена): вместо нового поля передавать `base_score` (скаляр) + `risk_factor` (скаляр) и пересчитывать `raw` на фронте как `role_scores[role] / risk_factor`. Отклонено, т.к. деление на `risk_factor` на фронте воспроизводит ту же хрупкую конструкцию, из-за которой возникла путаница (деление/умножение на риск-фактор в двух местах, риск рассинхронизации при округлении и при `risk_factor == 0`/`baseScore == 0`). Явное сырое поле с бэкенда — прямее и надёжнее.

**Frontend**: колонки по ролям и «Итого (чд)» в строке эпика (`reports-panel.js`, блок рендеринга per-epic row, ~строки 178-198) переключаются на `epic.raw_role_scores[roleName]` вместо `epic.role_scores[roleName]`. Итоговая сумма по всем эпикам (`totalRawScoreSum`, ~строка 214-221) считается из тех же сырых значений. «С рисками (чд)» и её сумма — без изменений (`epic.final_score`).

## Risks / Trade-offs

- [Расширение JSON-контракта] → некритично: новое поле, существующие консьюмеры API не ломаются.
- [Рассинхронизация: если для эпика нет `role_scores`, но появляется `raw_role_scores`, а фронт где-то ещё использует старое поле] → ограничить изменение только per-epic таблицей вместимости; другие потребители `role_scores` (если появятся) не трогать в рамках этого изменения.
- [Путаница в семантике `role_scores` для будущих читателей API] → зафиксировать в спеке (`capacity-report`) явно: `role_scores` — риск-скорректированные, `raw_role_scores` — сырые; закомментировать в структуре `EpicReportItem` при реализации.
