## Context

См. proposal.md - Why. Технические ограничения, влияющие на подход:

- `docker-compose.yml` намеренно не в git (правило в `.gitignore`,
  `git ls-files` подтверждает — файл не отслеживается) — там же хранятся
  реальные пароли БД и т.п. Это значит, что GitHub Actions **не может**
  задеплоить обновлённый `docker-compose.yml` вместе с кодом: файл живёт
  только на VPS и правится вручную. Джоба деплоя обязана работать с уже
  существующим на сервере `docker-compose.yml`.
- Существующие `run_docker_build.sh` и `scripts/deploy/deploy.sh`
  реализуют модель "собрать образ из исходников прямо на VPS" (`git pull`
  + `docker compose build --no-cache`) — они не тянут готовый образ и не
  оперируют версией/тегом образа. Новая модель (по требованию задачи)
  — Docker Hub как промежуточное хранилище версионированных образов —
  требует нового скрипта деплоя, а не модификации старого (старый
  остаётся рабочим ручным fallback-путём, см. proposal.md).
- Секреты сейчас частично хранятся в открытом виде в файлах на диске
  (см. CAUTION в `.agents/tasks/task_devops.md`) — пайплайн не должен
  логировать пароли/токены; Docker Hub credentials и SSH-ключ VPS
  передаются только через GitHub Secrets, не хардкодятся в workflow.
- VPS-адрес `85.239.57.254` уже упоминается в открытом виде в
  `task_devops.md`, но в самом workflow используется `secrets.VPS_HOST`,
  а не хардкод — секрет остаётся единственным источником адреса для
  пайплайна, изменение адреса не требует правки workflow.

## Goals / Non-Goals

**Goals:**
- Один workflow: push git-тега `vX.Y.Z` → собрать образ → опубликовать в
  Docker Hub с тегами `X.Y.Z` и `latest` → обновить контейнер на VPS до
  этой версии, с healthcheck и откатом при неудаче.
- Деплой-логика вынесена в версионируемый shell-скрипт (не инлайн в YAML),
  по аналогии с уже принятым в проекте подходом (`scripts/deploy/deploy.sh`).

**Non-Goals:**
- Не добавляется отдельная CI-джоба lint/test перед сборкой образа —
  задача ограничена сборкой/публикацией/деплоем по явному запросу
  пользователя; корректность кода на этапе сборки образа проверяется
  неявно самой компиляцией в Dockerfile (`go build` падает — сборка
  падает). Добавление lint/test — отдельная задача.
- Не переписывается `run_docker_build.sh`/`scripts/deploy/deploy.sh` —
  они остаются нетронутым ручным путём деплоя.
- Не автоматизируется одноразовая правка `docker-compose.yml` на VPS
  (файл вне git, вне досягаемости пайплайна) — только документируется
  как обязательный ручной шаг.
- Не заводятся сами GitHub Secrets — задача только объявляет, какие
  нужны; создание значений — ручное действие пользователя в настройках
  репозитория.

## Decisions

### 1. Триггер и версия — из git-тега, без отдельного bump-шага

```yaml
on:
  push:
    tags:
      - 'v*.*.*'
```

Версия для тегов образа берётся из `github.ref_name` с отрезанным
префиксом `v` (`1.2.3` из `v1.2.3`). Не вводится отдельный
автоматический bump/changelog-инструмент (semantic-release и т.п.) —
версию по-прежнему назначает человек, создавая тег; это осознанно
согласовано с пользователем (см. вопрос "Триггер сборки").

### 2. Docker Hub: имя образа и теги

Образ публикуется как `<DOCKERHUB_USERNAME>/epicscorebot` (репозиторий
Docker Hub создаётся/используется под существующим аккаунтом,
`DOCKERHUB_USERNAME` уже определяет namespace — второй секрет для имени
репозитория не нужен). На каждый push тега публикуются два тега образа:
точная версия (`1.2.3`) и `latest`. `latest` нужен только для удобства
ручного `docker pull` при отладке — деплой-скрипт всегда явно указывает
`X.Y.Z`, никогда не полагается на `latest`, чтобы деплой был
воспроизводим и не зависел от того, какой тег запушили последним.

### 3. Джоба deploy работает по готовому shell-скрипту, не инлайн-SSH-команды

Новый `scripts/deploy/deploy_image.sh <version>`:
- Сохраняет тег текущего запущенного образа (`docker inspect` контейнера
  `app-backend-service-epic-score-bot` → текущий image tag) для отката.
- `docker pull <repo>:<version>` (образ уже существует в Docker Hub на
  этом шаге — job зависит от build-and-push).
- **Предполагает**, что сервис `app-backend-service-epic-score-bot` в
  `docker-compose.yml` на VPS уже описан через `image: <repo>:${VERSION}`
  (переменная окружения, не хардкод версии в самом файле) — это тот
  самый одноразовый ручной шаг из proposal.md. Скрипт экспортирует
  `VERSION=<version>` перед `docker compose up`, чтобы docker-compose
  подставил нужный тег.
- `docker compose up -d --no-deps app-backend-service-epic-score-bot`.
- Healthcheck-цикл на `http://localhost:8080/ping` (тот же паттерн, что
  уже в `deploy.sh` — до 30 попыток с интервалом).
- При неудаче: `export VERSION=<сохранённый предыдущий тег>` →
  `docker compose up -d --no-deps ...` заново → лог ошибки; в отличие от
  `deploy.sh` откат не через `git reset --hard` (git здесь не источник
  истины для образа), а через переключение обратно на предыдущий тег
  образа.
- Логирование — тот же формат, что в `deploy.sh` (`log_msg` в
  `/var/log/epicscorebot-deploy.log`), для единообразия при чтении логов
  на сервере.

**Альтернатива (отклонена)**: инлайн SSH-команды прямо в YAML шага
`appleboy/ssh-action` (как в черновике `task_devops.md`). Отклонена —
проект уже установил конвенцию "деплой-логика — в версионируемом,
тестируемом на глаз shell-скрипте с логированием и rollback", менять её
для этой задачи нет причины; инлайн-YAML сложнее читать/поддерживать при
росте логики отката.

### 4. GitHub Actions job для SSH

`appleboy/ssh-action@v1` (используется в черновике `task_devops.md`,
широко распространён, не требует настройки собственного SSH-агента в
раннере) — вызывает на сервере
`bash /home/EpicScoreBot/scripts/deploy/deploy_image.sh <version>` (сам
скрипт уже должен быть на сервере — попадает туда через `git pull`
внутри самого скрипта деплоя как первый шаг, аналогично текущему
`deploy.sh`, чтобы не требовать отдельного шага копирования файлов по
SCP).

### 5. Зависимость джоб и условие запуска deploy

```yaml
jobs:
  build-and-push:
    ...
  deploy:
    needs: build-and-push
    runs-on: ubuntu-latest
    steps: [...]
```

`needs: build-and-push` — стандартный механизм GitHub Actions: `deploy`
не запускается, если `build-and-push` завершилась неудачей, реализует
согласованное "автоматически сразу после успешного push образа".

## Risks / Trade-offs

- [Ручной шаг на VPS перед первым релизом по новой схеме] → пока
  `docker-compose.yml` на сервере не переведён на `image: ...`, джоба
  deploy будет либо no-op, либо упадёт на `docker compose up` (сервис
  всё ещё настроен на `build:`) → явно задокументировать шаг в
  tasks.md/README, первый релиз по тегу не мержить до выполнения ручного
  шага на сервере.
- [SSH-ключ и Docker Hub token в GitHub Secrets] → стандартный риск
  компрометации CI-раннера; секреты не логируются
  (`appleboy/ssh-action`/`docker/login-action` не печатают значения),
  доступ к Secrets ограничен правами репозитория — не вводит новых рисков
  сверх обычных для GitHub Actions + приватный VPS.
- [Откат на предыдущий тег образа при неудачном healthcheck] → если
  предыдущий тег уже удалён с сервера локальным `docker image prune`,
  откат не сработает (образа нет локально) → `deploy_image.sh` должен
  делать `docker pull` предыдущего тега перед откатом (Docker Hub —
  источник истины, а не только локальный кэш образов).
- [Первая сборка по тегу для существующего проекта без истории версий]
  → нет предыдущего тега для сравнения при самом первом релизе → скрипт
  должен корректно обрабатывать случай "предыдущего тега нет" (не
  пытаться откатываться, просто сообщить об ошибке и выйти с ненулевым
  кодом).
