## Context

Мотивация — см. proposal.md «Why». Здесь только то, что формирует подход.

Текущий планировщик (`Service.RecalculateTeamSchedule` + `recalculateEpicSchedule`, `internal/gantt/ganttService.go`) — один прямой проход по очереди: эпики в порядке `epics.sort_order` → стори внутри эпика → группы ролей внутри стори по `defaultRoleOrder`. Вся ресурсная модель — одна карта:

```go
roleFreeAt := make(map[uuid.UUID]time.Time) // roleID -> эффективное окончание последней задачи роли
```

Дата старта листовой задачи считается как `moveToWorkDay(maxTime(target, roleNextAvailable, epicFloor))`, где `target = groupPrevEnd + StartOffsetDays`. Замороженные задачи (`Progress > 0` или `ActualEndDate != nil`) даты не пересчитывают, но своим эффективным окончанием двигают `roleFreeAt`.

Ограничения, которые нельзя игнорировать:

- **Пересчёт вызывается очень часто** — на генерацию, reorder эпика/стори, каждое изменение прогресса. Он же полностью переписывает даты. Значит любой новый расчёт должен быть идемпотентным при неизменном входе.
- **Перегенерация уничтожает строки**: `generateTaskRowsForEpic` делает `DeleteGanttTasksByEpicID` и создаёт строки заново. `createChild` не переносит `StartOffsetDays` — это уже сегодня работающий баг потери пользовательского ввода.
- **Связь строки Ганта со стори держится на сравнении имён**: `storyTasksByName[fmt.Sprintf("%s: %s", story.Number, story.Name)]`. Колонки `story_id` в `gantt_tasks` нет.
- **Стори — это строки `epics`** с `parent_epic_id` (`GetStoriesByEpicID` возвращает `[]domain.Epic`), поэтому один и тот же тип идентификатора адресует и стори, и legacy-эпик без стори.
- **`epic_id` у всех листовых задач эпика одинаков** — это ID верхнего эпика, а не стори. Пара `(gantt_tasks.epic_id, role_id)` не уникальна.
- **Пересчёт сериализован per-team** (`scheduleMu`, `sync.Map`), общей БД-транзакции нет.
- **`GetRoleByUserID` возвращает одну роль на пользователя**, хотя `user_roles` — M:N. Для пула он непригоден; `GetUsersByTeamIDAndRoleID` (`internal/repositories/user.go`) M:N учитывает и уже существует.

## Goals / Non-Goals

**Goals:**

- Заменить единицу занятости с роли на исполнителя, сохранив прежнюю структуру одного прямого прохода планировщика.
- Сделать распределение исполнителей воспроизводимым: один и тот же вход — один и тот же результат.
- Отделить пользовательский ввод (закрепление исполнителя, смещение старта) от производного состояния диаграммы так, чтобы он переживал перегенерацию по построению, а не за счёт аккуратности кода перегенерации.
- Устранить существующую потерю `start_offset_days` тем же механизмом.

**Non-Goals:**

- Дробление одной задачи между несколькими исполнителями (двое делают 10-дневную задачу за 5 дней) — одна задача, один исполнитель.
- Учёт скорости/производительности конкретного человека. `User.Weight` — вес голоса в скоринге, а не velocity; смешивать их нельзя.
- Ресурсный вид диаграммы (дорожка на человека вместо дорожки на задачу).
- Учёт отпусков, календарей отсутствий, частичной занятости.
- Кросс-командная загрузка (см. Решение 8).
- Оптимальность расписания в смысле теории расписаний. Задача NP-трудна; берётся жадная эвристика (Решение 2).

## Decisions

### Решение 1. Единица занятости — исполнитель, ролевой календарь остаётся запасным путём

`roleFreeAt` дополняется картой по исполнителю, а не заменяется ею:

```go
pools          map[uuid.UUID][]domain.User // roleID -> кандидаты, отсортированы по ID
assigneeFreeAt map[uuid.UUID]time.Time     // userID -> эффективное окончание последней задачи
roleFreeAt     map[uuid.UUID]time.Time     // roleID -> то же, ТОЛЬКО для ролей с пустым пулом
rrCursor       map[uuid.UUID]int           // roleID -> курсор round-robin
```

Развилка при выборе календаря для задачи:

```
заморожена (Progress > 0 | ActualEndDate != nil)
    → исполнитель читается из gantt_tasks.assignee_id, НЕ пересчитывается
пул роли пуст
    → исполнителя нет, календарь роли (прежнее поведение)
есть действующее закрепление
    → закреплённый человек, его календарь
иначе
    → автоматический выбор (Решение 2)
```

*Почему не выбросить `roleFreeAt` совсем:* команда может иметь оценку по роли, носителей которой в ней нет (см. спеку, «Роль без кандидатов планируется как единый ресурс»). Без ролевого календаря такие задачи легли бы все на одну дату и наложились друг на друга — это было бы регрессией относительно сегодняшнего поведения. Альтернатива «блокировать генерацию, пока роль не укомплектована» отвергнута: она заблокировала бы массовую перегенерацию квартала целиком из-за одной незакрытой роли.

### Решение 2. Жадный выбор по получаемой дате старта, round-robin как тай-брейк

Кандидат выбирается не по минимальному `assigneeFreeAt`, а по минимальной **фактически получаемой дате старта**:

```go
start(u) = moveToWorkDay(maxTime(
    groupPrevEnd.AddDate(0, 0, offset),      // FS-зависимость внутри стори + lead/lag
    epicFloor,                               // общекомандный пол
    nextWorkDay(assigneeFreeAt[u]),          // занятость конкретного человека
))
```

Выбирается `argmin start(u)`; при равенстве — следующий по `rrCursor[roleID]`.

*Почему не argmin по `assigneeFreeAt`:* если задача всё равно не может начаться раньше окончания аналитика этой же стори, то все, кто освобождается до этой даты, дают одинаковый старт и равноценны. Минимизация `freeAt` в этой ситуации выбирала бы «самого свободного» произвольно и без пользы.

*Почему round-robin нужен именно как тай-брейк, а не как основная политика:* строгий round-robin при разной длительности задач заметно хуже жадного (BE-пул {A, B}, очередь 6д/2д/2д: RR даёт makespan 8, жадный — 6). Но в начале квартала все кандидаты свободны, и равенство дат старта — не редкий случай, а типичный; там решает именно тай-брейк.

*Почему тай-брейк обязан быть детерминированным:* итерация `map` в Go рандомизирована. Без явного порядка одинаковые входные данные давали бы разное распределение при каждом пересчёте, а пересчёт срабатывает на любое изменение прогресса. Исполнители «мигали» бы по диаграмме без причины. Отсюда два требования: `pools[roleID]` отсортирован по `uuid` (стабильный ключ, не зависящий от порядка выдачи БД), а `rrCursor` пересоздаётся в начале каждого вызова `RecalculateTeamSchedule` — ровно как `roleFreeAt` сегодня, чтобы не накапливать состояние между вызовами.

### Решение 3. Приоритет закрепления — над выбором человека, но не над датой

Закрепление обрабатывается в том же единственном проходе, как жёсткое ограничение «кто», а не как отдельная фаза. Задача ждёт освобождения закреплённого человека, даже если свободный кандидат дал бы более ранний старт.

*Почему не двухфазный вариант «сначала расставить все закрепления, потом жадно заполнить остальное»:* он неисполним. Чтобы поставить закреплённую задачу, нужна её дата старта, а та зависит от задач более ранних групп ролей той же стори, которые могут быть назначены автоматически, — которые, в свою очередь, зависят от занятости, формируемой закреплениями. Циклическая зависимость. Единственный способ её разорвать — тот же топологический порядок, по которому планировщик и так идёт.

*Следствие, которое нужно донести до пользователя:* закрепление может отодвинуть задачу и всё, что за ней по конвейеру. Это не баг, а цена ручного управления, и UI должен показывать новую дату после сохранения (штатная перерисовка после пересчёта это уже обеспечивает).

### Решение 4. Пользовательский ввод — отдельная таблица, ключ `(epic_id, role_id)`

```sql
CREATE TABLE task_assignments (
    epic_id           UUID NOT NULL REFERENCES epics (id) ON DELETE CASCADE,
    role_id           UUID NOT NULL REFERENCES roles (id) ON DELETE CASCADE,
    user_id           UUID     NULL REFERENCES users (id) ON DELETE SET NULL,
    start_offset_days INT  NOT NULL DEFAULT 0,
    PRIMARY KEY (epic_id, role_id)
);
```

`epic_id` здесь — идентификатор **стори** (или самого эпика для legacy-эпиков без стори). Благодаря тому, что стори живут в таблице `epics`, ключ единообразен для обоих случаев.

Разделение ответственности получается симметричным уже существующему:

```
ВВОД (намерение человека)              ВЫВОД (считает планировщик)
  epics.sort_order                       gantt_tasks.start_date / end_date
  task_assignments.user_id               gantt_tasks.assignee_id
  task_assignments.start_offset_days     gantt_tasks.progress
  ↑ переживает DeleteGanttTasksByEpicID  ↑ пересоздаётся свободно
```

`gantt_tasks.assignee_id` — **результат** расчёта, как и даты, а не источник истины. Единственное исключение — замороженные задачи, для которых он и есть источник (Решение 6).

*Почему не колонка `assignee_id` в `gantt_tasks` как источник истины:* перегенерация удаляет строки, закрепления исчезали бы. Восстанавливать их пришлось бы отдельным кодом в `generateTaskRowsForEpic` — ровно тем механизмом, который сегодня уже не сработал для `start_offset_days`. Отдельная таблица делает устойчивость свойством схемы, а не дисциплины.

*Почему не добавить `story_id` в `gantt_tasks` и не хранить ввод там:* колонка `story_id` убрала бы хрупкое сравнение имён и сама по себе полезна, но источником истины для пользовательского ввода строка Ганта всё равно быть не может по причине выше. Добавление `story_id` — самостоятельное улучшение, в этот change не входит.

`ON DELETE SET NULL` у `user_id` вместо каскада: удаление пользователя не должно молча стирать закрепление вместе со смещением старта в той же строке. `user_id IS NULL` при этом означает ровно «автоматически», что совпадает с семантикой снятия закрепления.

### Решение 5. Переезд `start_offset_days`, но без удаления исходной колонки

Миграция `011_task_assignees.sql`:

1. создаёт `task_assignments`;
2. добавляет `gantt_tasks.assignee_id UUID NULL REFERENCES users (id) ON DELETE SET NULL`;
3. переносит ненулевые смещения, восстанавливая связь «строка → стори» тем же сравнением имён, что использует планировщик:

```sql
INSERT INTO task_assignments (epic_id, role_id, start_offset_days)
SELECT COALESCE(s.id, gt.epic_id), gt.role_id, gt.start_offset_days
FROM gantt_tasks gt
JOIN gantt_tasks p ON p.id = gt.parent_task_id
LEFT JOIN epics s
       ON s.parent_epic_id = gt.epic_id
      AND s.number || ': ' || s.name = p.name
WHERE gt.role_id IS NOT NULL AND gt.start_offset_days <> 0
ON CONFLICT (epic_id, role_id) DO NOTHING;
```

Колонка `gantt_tasks.start_offset_days` **остаётся** — мигратор проекта (`internal/migrator`) forward-only, файлы применяются по порядку имён, down-миграций нет. Удаление колонки в этой же миграции сделало бы откат релиза невозможным без восстановления БД из бэкапа. Удаление выносится в отдельную миграцию после проверки на проде; до тех пор колонка не читается и не пишется.

*Риск сравнения имён:* если стори переименовали после генерации задач, `LEFT JOIN` не совпадёт и смещение уедет на `gt.epic_id` (ключ верхнего эпика). Это не регрессия — сегодня такое смещение теряется полностью при первой же перегенерации, — но и не идеал. Приемлемо: `start_offset_days <> 0` на реальных данных единицы строк.

### Решение 6. Замороженная задача — закрепление по факту

Задача с `Progress > 0` или `ActualEndDate != nil` сохраняет `assignee_id` и не участвует в автоматическом распределении. Её эффективное окончание (`ActualEndDate ?? EndDate`) двигает `assigneeFreeAt` её исполнителя — так же, как сегодня двигает `roleFreeAt`.

*Почему:* иначе изменение состава команды или порядка эпиков могло бы переназначить наполовину сделанную задачу другому человеку — расписание перестало бы соответствовать тому, что происходит в реальности.

*Следствие:* `gantt_tasks.assignee_id` для замороженных задач читается **до** пересчёта, то есть проход планировщика должен получать предыдущее значение колонки, а не пустое. Это выполняется само собой — `GetGanttTasksByEpicID` уже возвращает строки целиком.

### Решение 7. Недействующее закрепление не удаляется

Если закреплённый человек больше не кандидат роли (вышел из команды или лишился роли), задача уходит в автоматическое распределение, но строка в `task_assignments` сохраняется. Вернётся человек в пул — закрепление снова начнёт действовать.

*Почему не удалять:* удаление — необратимая потеря намерения из-за события, к задаче отношения не имеющего (админ поправил роли). API отдаёт признак, что закрепление есть, но не действует, чтобы UI не показывал закрепление работающим. Альтернатива «считать ошибкой и не пересчитывать расписание» отвергнута: пересчёт запускается фоново из множества мест, падать там из-за кадровых изменений нельзя.

### Решение 8. Загрузка считается в границах команды

`assigneeFreeAt` живёт внутри одного вызова `RecalculateTeamSchedule` и не пересекается между командами. Человек в двух командах получает два независимых календаря.

*Почему не глобально:* общий календарь сделал бы пересчёт одной команды меняющим график другой, а существующей per-team блокировки (`scheduleMu`) стало бы недостаточно — потребовалась бы глобальная сериализация всех пересчётов. Это отдельное архитектурное изменение с заметной ценой по параллелизму, несоразмерное задаче. Текущая семантика («команда планируется автономно») сохраняется.

### Решение 9. Состав команды — отдельный эндпоинт

```
GET /api/gantt/teams/{id}/members
→ { "members": [ { "id", "first_name", "last_name", "role_ids": ["…"] } ] }
```

*Почему не встраивать `roster` в `GET /api/gantt/tasks`:* этот эндпоинт дёргается на каждое изменение прогресса и после каждого reorder; состав команды при этом не меняется. Таскать его в каждом ответе — постоянные накладные расходы ради экономии одного запроса при открытии вкладки.

*Почему не переиспользовать состав, вшитый в ответ по оценкам эпика:* он строится через `GetRoleByUserID`, возвращающий **одну** роль на пользователя, тогда как `user_roles` — M:N. Для выпадающего списка кандидатов это дало бы неверный пул: участник с двумя ролями попал бы только в одну. Новый эндпоинт строится на корректном `GetUsersByTeamIDAndRoleID` / выборке ролей пачкой.

Пул внутри планировщика берётся тем же `GetUsersByTeamIDAndRoleID`, один раз на роль за вызов пересчёта (роли на команду — единицы), а не на каждую задачу.

### Решение 10. Исполнитель в подписи задачи

Имя исполнителя добавляется в подпись задачи (левая колонка списка задач Frappe Gantt).

*Почему не бейдж на баре:* требует ручного DOM-патчинга в `applyPostRenderEnhancements` и разваливается в режиме «Месяц», где бары узкие. *Почему не отдельная колонка:* Frappe Gantt 1.2.2 не поддерживает пользовательские колонки, пришлось бы строить свою разметку поверх библиотеки.

*Почему это не косметика:* до этого изменения два бара одной роли не могли пересекаться по времени конструктивно. Теперь пересекаются регулярно, и без имени исполнителя одинаково окрашенные накладывающиеся бары неразличимы — диаграмма перестаёт читаться.

## Risks / Trade-offs

**Недетерминированный порядок итерации `map` в Go даёт «мигающих» исполнителей** → пул сортируется по `uuid`, `rrCursor` пересоздаётся на каждый вызов; в тестах — явная проверка, что два последовательных пересчёта без изменения входа дают идентичное распределение.

**Изменение состава команды перетасовывает исполнителей на ещё не начатых задачах** → это неизбежно (пул изменился — жадный выбор изменился) и в целом корректно. Смягчение: замороженные задачи не переназначаются (Решение 6), а всё важное закрепляется вручную.

**Закрепление ухудшает расписание, и пользователь не понимает почему** → UI после сохранения показывает пересчитанные даты; в модалке — пояснение, что закрепление гарантирует исполнителя, а не дату.

**Перенос `start_offset_days` промахивается на переименованных стори** → не регрессия (сегодня значение теряется полностью), объём затронутых строк мал; исходная колонка не удаляется, поэтому данные остаются восстановимыми.

**Жадная эвристика даёт не оптимальный makespan** → сознательный размен: задача NP-трудна, а предсказуемость и объяснимость расписания важнее последних процентов плотности. Ручное закрепление — предохранительный клапан для случаев, где человек знает лучше.

**Рост числа запросов к БД в пересчёте** (пулы ролей, закрепления) → читать пачкой на команду в начале `RecalculateTeamSchedule`, а не внутри цикла по задачам. Пересчёт и сегодня делает `GetRoleByID` в цикле — новый код не должен усугублять этот паттерн.

**Пересекающиеся бары одной роли ломают привычное чтение диаграммы** → имя исполнителя в подписи (Решение 10); задачи без исполнителя и недействующие закрепления помечаются отдельно.

## Migration Plan

1. Миграция `011_task_assignees.sql` применяется автоматически при старте контейнера существующим `internal/migrator` (forward-only, по порядку имён файлов). Отдельных действий DevOps не требуется.
2. После деплоя `gantt_tasks.assignee_id` у существующих задач пуст. Первый же пересчёт расписания команды (генерация, reorder, изменение прогресса) заполняет его. Для немедленного заполнения достаточно массовой перегенерации квартала либо любого reorder.
3. Замороженные задачи, созданные до изменения, имеют пустой `assignee_id`. Они остаются без исполнителя (переназначать их автоматом нельзя по Решению 6) — при необходимости исполнитель проставляется вручную закреплением.
4. **Откат:** мигратор down-миграций не поддерживает. Схема после `011` обратно совместима с предыдущей версией кода — новая таблица и новая колонка просто не используются, а `gantt_tasks.start_offset_days` намеренно сохранён и содержит прежние значения. Поэтому откат образа на предыдущий тег работает без вмешательства в БД. Это и есть причина не удалять колонку в этой миграции.
5. Удаление `gantt_tasks.start_offset_days` — отдельная миграция в следующем релизе, после подтверждения, что новая схема работает на проде.
