# UX-постановка для фронтенда (задача 4.1)

Составлена субагентом `ux` (код не пишет). Реализуется задачами 5.1–5.4.
Опирается на design.md Решения 3, 7, 10 и требования spec.md об отображении
исполнителя на диаграмме.

## Состояния, приходящие с бэкенда

Четыре состояния различаются парой булевых плюс наличием `assignee_id`:

1. **Авто** — `assignee_id` есть, `assignee_is_manual=false`, `assignee_pin_invalid=false`
2. **Закреплён и работает** — `assignee_id` есть, `is_manual=true`, `pin_invalid=false`
3. **Закрепление недействительно** — `assignee_id` есть (ФАКТИЧЕСКИЙ, не закреплённый!), `is_manual=false`, `pin_invalid=true`
4. **Нет кандидатов** — ключа `assignee_id` в ответе нет

## 1. Подача исполнителя в подписи задачи (задача 5.2)

**Формат:** `{имя роли} — {фамилия}`, где фамилия — последнее слово `assignee_name`
(`assignee_name.trim().split(/\s+/).pop()`). Пример: `BE разработчик — Константинопольский`.

**Почему фамилия, а не полное имя:** `assignee_name` приходит как «Имя Фамилия»
(`handlers/gantt.go:340`). Отбрасывание имени — самое дешёвое по риску сокращение:
чистая строковая операция в `renderGantt()`, без новой DOM/SVG-логики и без риска
сломать инкрементальный `refresh()`. Полностью проблему длинных фамилий это не
решает, и это осознанно: design.md Решение 10 отверг ручной DOM-патчинг бара
именно из-за хрупкости в режиме «Месяц». Компрессия текста через SVG
`textLength`/`lengthAdjust` дала бы предсказуемую ширину, но добавляет ровно тот
тип сложности, которого design.md избегает — без явного запроса не вводить.

**Переполнение:** ничего специального — не обрезать, не переносить. Frappe Gantt
1.2.2 сам выносит не поместившуюся подпись вправо от бара (`.bar-label.big`, уже
стилизован в `gantt.css:117-121`) — то же штатное поведение, что сегодня у длинных
названий эпиков. Новой категории проблемы не создаётся.

**Только для ролевых задач с исполнителем** (`role_id` и `assignee_id` присутствуют).
Родительские бары не трогать. Задача без исполнителя — подпись остаётся чистым
именем роли: текстовый суффикс «нет исполнителя» на каждой такой задаче будет
шумом, когда в команде вообще нет носителей роли (достаточно отличия бара, п. 3).

- **Файл:** `web/gantt/js/gantt-renderer.js`, `renderGantt()`, блок
  `const ganttTasks = tasks.map(...)` (~строки 137–159), рядом с веткой `level === 3`.
- **Не трогать:** `cleanTaskName()`, `getTaskClass()`, tree-префиксы `└─`.
- **Приёмка:** роль с исполнителем — подпись содержит `{роль} — {фамилия}`; роль без
  исполнителя — без изменений; во всех трёх режимах подпись видна, переключение
  режима не роняет рендер и не плодит новых DOM-слушателей.

## 2. Выбор исполнителя в модалке деталей задачи (задача 5.1)

Новый `form-group` в `#task-details-modal .modal-body`, **между** блоком «Факт» и
блоком «Прогресс выполнения» — порядок «кто → сколько сделано» логичнее обратного:

```html
<div class="form-group" id="task-details-assignee-group">
    <label for="task-details-assignee">Исполнитель</label>
    <select id="task-details-assignee" class="select"></select>
    <div id="task-details-assignee-help" class="form-help"></div>
</div>
```

Существующие id (`task-details-progress`, `task-details-offset`, `task-details-save`
и т.д.) не менять.

### Пять состояний селекта и текста под ним

| Состояние | Опции селекта | Выбрано | Текст в `form-help` |
|---|---|---|---|
| **Загрузка** (идёт `GET /teams/{id}/members`) | одна опция «Загрузка исполнителей…», `disabled` | — | пусто |
| **1. Авто** | «Автоматически» + все кандидаты роли | `""` | «Сейчас задачу ведёт {assignee_name} — назначен автоматически. Закрепление гарантирует исполнителя, но не дату: если он занят другими задачами, старт задачи сдвинется на его освобождение.» |
| **2. Закреплён и работает** | то же | `assignee_id` | «Закреплено за {assignee_name}. Закрепление гарантирует исполнителя, но не дату: если он занят другими задачами, старт задачи сдвинется на его освобождение.» |
| **3. Закрепление недействительно** | то же | `""` | `color: var(--color-warning)`: «Ручное закрепление на эту задачу есть, но закреплённый ранее человек больше не кандидат этой роли в команде (потерял роль или покинул её). Сейчас задачу автоматически ведёт {assignee_name}. Закрепление вернётся в силу, если этот человек снова станет кандидатом, либо будет заменено, если вы выберете здесь другого.» |
| **4. Нет кандидатов** | только «Автоматически» | `""` | «В команде нет участников с ролью «{имя роли}». Задача останется без исполнителя, пока в команде не появится участник с этой ролью.» |

**Почему в состоянии 3 селект показывает «Автоматически», а не имя закреплённого:**
контракт API не отдаёт, КТО был закреплён — только фактического исполнителя и флаг
`is_manual=false`. Показать выбранным пункт с именем фактического человека было бы
враньём: создало бы видимость нового ручного закрепления на него, которого нет.
«Автоматически» — единственный пункт, честно отражающий `is_manual=false`;
разъяснение уносится в предупреждающий текст под селектом.

### Критичное правило сохранения намерения

При открытии модалки запомнить исходное значение селекта (`""` для состояний 1/3/4,
`assignee_id` для состояния 2) — так же, как уже делается для прогресса/смещения
(`currentDetailsOriginal`, `gantt-renderer.js:447`). `PUT /tasks/{id}/assignee`
отправлять **только если пользователь реально изменил значение** относительно
исходного.

Без этого в состоянии 3 (селект по умолчанию показывает `""`) простое нажатие
«Сохранить» без изменения выбора отправит `{"user_id": null}` и снимет дремлющее
закрепление, которое по требованию «Закрепление на выбывшего из пула кандидата»
должно сохраняться в ожидании возврата человека в пул. Это тихая потеря
пользовательского намерения.

### Загрузка кандидатов и ошибки

Кандидатов получать через `GET /api/gantt/teams/{teamId}/members` **напрямую внутри
`openTaskDetailsModal()`** в `gantt-renderer.js` — по аналогии с уже существующим
`openStoryReorderModal()`, который так же напрямую дёргает `apiGet` (~строки 733–751).
При каждом открытии заново, без кеша: гарантирует свежесть состава при возврате
человека в пул. Отдельная обёртка в `api.js` не требуется — использовать
существующий универсальный `apiPut(path, body)`.

Кандидаты роли = участники, у кого `role_ids` содержит `role_id` текущей задачи.
Опции подписывать как `${first_name} ${last_name}` — тот же формат, что уже
используется в `scoring-panel.js:1056`.

**Ошибка загрузки:** селект показывает одну неактивную опцию «Ошибка загрузки
исполнителей», `disabled`, `form-help` пуст, показывается toast с `err.message`
(без кода/JSON). Остальная модалка остаётся рабочей — ошибка загрузки исполнителей
не должна блокировать сохранение прогресса.

### Отправка

`""` конвертировать в JS `null` перед отправкой: `{"user_id": selected || null}` —
API ожидает буквальный `null`, а не пустую строку.

Порядок в `saveTaskDetails()`: сначала `PUT /tasks/{id}/assignee` (если изменился),
затем существующий `PUT /tasks/{id}` с прогрессом/смещением (если изменились). Оба в
одном try/catch; если один упал — всё равно выполнить `reloadCurrentTeamTasks()` в
конце (в том числе в catch), чтобы диаграмма не разошлась с состоянием бэкенда,
затем toast с текстом ошибки, модалку не закрывать (как и сегодня).

**Блокировка кнопок (закрывает найденный дефект соседнего кода):** `#task-details-save`
и `#task-details-cancel` сейчас остаются активными на время `apiPut`, поэтому двойной
клик уходит двумя параллельными запросами. Это уже баг сегодняшнего кода
(прогресс/смещение), а мы добавляем туда же третий запрос. Поставить `disabled` в
начале и снять в `finally` — как уже сделано в `app.js:410–447` (`runRegenerateQuarter`).

- **Приёмка:** для каждого из 5 состояний селект и текст соответствуют таблице;
  сохранение без изменения выбора в состоянии 3 не отправляет `PUT .../assignee`;
  выбор кандидата и «Автоматически» отправляют корректное тело; кнопки заблокированы
  на время запроса и разблокированы в `finally`.

## 3. Индикация на диаграмме (задача 5.3)

«Нет исполнителя» и «недействующее закрепление» — два разных состояния и по
спецификации, и по риску: первое — нейтральный факт (в команде нет носителя роли),
второе — коварный случай, где показанный человек не тот, кто закреплён (design.md
Решение 7). Кодировать одинаково нельзя.

**Классы добавлять только через `applyPostRenderEnhancements()`** (`classList.add()`
на `.bar-wrapper`), **не через `custom_class`**. Причина двойная: Frappe Gantt 1.2.2
не поддерживает несколько custom-классов (комментарий в `gantt-renderer.js:328–335` —
браузер выбросит DOMException), а `custom_class` уже безусловно занят сервером под
цвет роли (`handlers/gantt.go:375–389`). Попытка передать составной класс либо уронит
рендер, либо потеряет цвет роли. Безопасный путь — тот же приём, что уже используется
для `gantt-completed`.

`web/gantt/css/gantt.css`:

```css
/* Нет исполнителя — роль без кандидатов: гасим роль-цвет, пунктир
   сигнализирует «не укомплектовано». :not() вместо порядка объявлений —
   чтобы не зависеть от каскада, если блоки позже переставят местами. */
.gantt .bar-wrapper.gantt-no-assignee:not(.gantt-completed) .bar {
    fill: var(--bg-tertiary);
    stroke: var(--text-muted);
    stroke-width: 1.5px;
    stroke-dasharray: 4 3;
    opacity: 0.6;
}
.gantt .bar-wrapper.gantt-no-assignee:not(.gantt-completed) .bar-progress {
    fill: var(--text-muted);
    opacity: 0.5;
}

/* Недействующее закрепление — роль-цвет сохраняется (работу реально ведёт
   показанный человек), тонкий предупреждающий пунктирный контур. */
.gantt .bar-wrapper.gantt-pin-invalid .bar {
    stroke: var(--color-warning);
    stroke-width: 2px;
    stroke-dasharray: 2 2;
}
.gantt .gantt-pin-invalid-icon {
    fill: var(--color-warning);
    font-size: 12px;
    font-weight: 700;
    pointer-events: none;
}
```

В `applyPostRenderEnhancements(tasks)` — по аналогии с существующей веткой
`isTaskCompleted`:

```js
if (!t.is_parent && t.role_id && !t.assignee_id) {
    wrapper.classList.add('gantt-no-assignee');
}
if (!t.is_parent && t.assignee_pin_invalid) {
    wrapper.classList.add('gantt-pin-invalid');
    // SVG <text> "⚠", x = x + 6, y = y + height/2 + 4, text-anchor: start —
    // левый край бара, симметрично галочке gantt-completed-icon у правого
    // края, чтобы метки не перекрывались, если задача одновременно
    // завершена и с недействующим закреплением.
}
```

**Приоритет при пересечении с `gantt-completed`** (задача одновременно завершена и без
исполнителя — редкий, но возможный кейс: прогресс можно проставить и без
исполнителя): побеждает стиль завершённости, что гарантирует селектор
`:not(.gantt-completed)` независимо от порядка объявления классов.

- **Не трогать:** `getTaskClass()`, серверный `custom_class`.
- **Приёмка:** роль без кандидатов — бар пунктирный, приглушённый, без цвета роли;
  недействующее закрепление — цвет роли сохранён, добавлен предупреждающий контур и
  иконка `⚠`; обычная задача — без изменений; завершённая и без исполнителя —
  выглядит как завершённая.

## 4. Сообщение о том, что закрепление гарантирует человека, но не дату

Реализуется текстом в `#task-details-assignee-help` (таблица в п. 2, состояния 1 и 2).
Присутствует **всегда**, когда исполнитель определён — и в авто-, и в ручном режиме,
а не только после закрепления: design.md (Risks) требует объяснить механику заранее,
до того как пользователь закрепит кого-то и удивится сдвигу даты. Тот же принцип, что
уже применён к `#task-details-offset` — там поясняющая строка есть постоянно,
независимо от текущего значения поля (`index.html:585–587`).

## 5. Скрытие управления исполнителем для `member` (задача 5.4)

Признак — **`isReadOnly = !userProfile || userProfile.role === 'member'`**, уже
определённый в `renderGantt()` (`gantt-renderer.js:162`) и используемый для
`readonly`/`readonly_dates` и гейта `on_click`. Вынести в общий хелпер
(`isGanttReadOnly()`) и переиспользовать в `openTaskDetailsModal()` — чтобы два места
гарантированно не разошлись со временем.

При `isReadOnly === true` — `#task-details-assignee-group.classList.add('hidden')`, тем
же приёмом, что уже применён к `#task-details-fact-group` (~строки 430–440). Это защита
в глубину: сегодня `on_click` и так не даёт `member` открыть модалку вовсе (гейт не
трогать), но критерий 5.4 должен проверяться независимо от внешнего гейта.

Не путать со вторым, независимым механизмом в `app.js:93–106` (`profile.role === 'member'`
для скрытия кнопок тулбара) — это другой набор элементов, его трогать не нужно.

- **Приёмка:** под `member` `#task-details-assignee-group` скрыт даже при прямом вызове
  `openTaskDetailsModal()`, независимо от гейта `on_click`.

## Решения пользователя по вынесенным вопросам

Оба вопроса, вынесенных `ux` наверх, пользователь решил — они входят в объём заявки
задачами 5.5 и 5.6.

1. **Доступ `member` к информации о задаче — делаем попап (задача 5.5).** `member` не
   может открыть модалку вовсе (`on_click` гейтится `isReadOnly` целиком), поэтому
   единственный канал task-уровня информации для него — встроенный попап Frappe Gantt.
   **Уточнение по факту реализации:** опция называется `popup`, а не `custom_popup_html` — последнее имя из версии 0.x библиотеки. Проверено по бандлу `frappe-gantt@1.2.2` с того же CDN, что грузит `index.html`: `custom_popup_html` в нём не встречается, дефолт объявлен как `popup: n => {...}`.

   Переопределить его так, чтобы для ролевого бара он нёс строку
   состояния: «Назначен автоматически» / «Закреплён вручную» / «⚠ Закрепление
   недействительно — работает автоматически» / «Нет исполнителя — нет участников с этой
   ролью в команде».

   Для родительских баров (эпик/стори) содержимое попапа должно остаться ровно таким,
   как сегодня по умолчанию. В проекте нет локальной копии исходников библиотеки — она
   грузится с CDN (`index.html:11,650`), — поэтому дефолтную разметку попапа Frappe
   Gantt 1.2.2 **сверить фактически в браузере/девтулах** и воспроизвести один в один,
   иначе переопределённый попап станет регрессией для существующего вида диаграммы.

   Гейт `on_click` по `isReadOnly` при этом не трогать — read-only модалку для `member`
   пользователь не выбрал.

2. **Легенда — делаем (задача 5.6).** Компактная легенда на вкладке «Гант» по **всем**
   состояниям бара, а не только по двум новым: цвета ролей, завершённость, факт-маркер,
   нет исполнителя, недействующее закрепление. Половинчатая легенда (только новое) хуже
   отсутствующей. Использовать те же токены и классы, что и сама диаграмма; не ломать
   вёрстку тулбара на узких экранах (Telegram WebApp — почти всегда мобильный клиент).
