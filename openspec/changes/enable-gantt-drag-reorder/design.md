## Context

См. `proposal.md` — мотивация. Технический контекст (весь код в `web/gantt/js/gantt-renderer.js`, если не указано иное):

- Frappe Gantt 1.2.2 подключён через CDN (`index.html:11,631`), не npm-зависимость. **Уточнено при реализации (2026-09-03) сверкой с реальным бандлом с CDN**: полный список событий, которые библиотека реально диспетчеризует (`trigger_event`) — `click, date_change, date_click, double_click, hover, progress_change, view_change`. Отдельного `on_after_date_change` в 1.2.2 **не существует** (в проверенной ранее вторичной документации он упоминался неточно) — это было ошибочным допущением исходной версии этого документа, см. Decision 1 ниже, как это компенсировано. `date_change` стреляет из `update_bar_position()`, вызываемого на каждый `mousemove` во время драга (может сработать много раз за один драг) и потенциально ещё раз на `mouseup` — но это тот же самый колбэк, не отдельное событие, и на `mouseup` часто не стреляет вовсе (нет дельты позиции с последнего `mousemove`). `readonly_dates` — **глобальная** опция конструктора, нет поля на уровне отдельной задачи для точечного «эту задачу можно тащить, эту нет».
- Сейчас `readonly_dates: true` (строка 118) блокирует драг вообще для всех баров на уровне библиотеки (скрывает resize-хендлы). `on_date_change` (строка 131) — вторая линия обороны: если дата всё же поменяется, показывает toast и делает полный `renderGantt()`.
- `renderGantt(tasks)` (строка 39) при КАЖДОМ вызове делает `container.innerHTML = ''` (строка 101) и `new Gantt(container, ...)` (строка 106) — полное пересоздание. Вызывается через `state.subscribe('tasks', renderGantt)` — то есть после любого изменения списка задач, не только после reorder.
- Иерархия: `getTaskLevel()` (строка ~63) определяет уровень по `parent_task_id`/`parent_id`: 1 = эпик (нет родителя), 2 = стори (родитель — эпик без родителя), 3 = ролевая задача (родитель — стори). В данные задачи для Frappe Gantt уже прокинуты `_is_parent`, `_parent_id`, `_sort_order`, `_role_id` (строки ~85-93).
- `on_click` (строка 123): клик по `_is_parent` бару → `openReorderModal` (список детей, Y-координатный drag в модалке); клик по листовому бару → `openTaskDetailsModal` (%, offset).
- Существующий Y-координатный reorder внутри модалки (`setupDragAndDropForModal`, строка 542; `saveOrder`, строка 587) — референсный алгоритм: при `dragover` находит `nextSibling` по Y-координате курсора относительно `getBoundingClientRect()` соседей, физически переставляет DOM-элемент; при сохранении — renumber'ит ВСЕ элементы по их итоговой DOM-позиции (`updateModalInputsOrder`, строка 572, просто `index + 1`) и шлёт `PUT .../reorder` для каждого элемента, чей номер изменился относительно исходного.
- Backend: `PUT /epics/{id}/reorder` и `PUT /stories/{id}/reorder` (`internal/gantt/ganttService.go:794,823`) уже существуют, используются модалкой без изменений. **Важно**: `UpdateEpicSortOrder` (`internal/repositories/epic.go:469`) — примитивный `UPDATE epics SET sort_order = $1 WHERE id = $2`, **без автоматического сдвига соседей**. Ответственность за пересчёт и рассылку новых номеров всем сдвинутым соседям — целиком на фронтенде (см. `saveOrder`). Оба эндпоинта в конце вызывают `RecalculateTeamSchedule` и возвращают `{"message": ..., "count": N}` — не обновлённый список задач, фронтенд обязан перезапросить задачи отдельно (`reloadCurrentTeamTasks`, строка 387).

## Goals / Non-Goals

**Goals:**
- Драг эпиков/историй прямо на графике, интерпретируемый как reorder, с теми же гарантиями консистентности sort_order, что уже даёт модалка.
- Устранить полный teardown/rebuild диаграммы при любом обновлении задач (включая уже существующий модалкой reorder — выигрыш общий для обоих путей).
- Не трогать бэкенд.

**Non-Goals:**
- Драг листовых (ролевых) задач — вне скоупа первой итерации (см. `proposal.md`).
- Вариант B (optimistic pin + settle-анимация) — отложен, делаем только если вариант A будет визуально неудовлетворителен.
- Ручной override дат в обход планировщика — не рассматривается.
- Кросс-родительский drag (перетащить стори в другой эпик, эпик в другую команду) — вне скоупа.
- Модалки «Порядок…» не удаляются и не меняются функционально — drag на графике им не замена, а дополнение.

## Decisions

### 1. Блокировка драга ролевых задач — через перехват события, не через библиотечный per-task readonly
Frappe Gantt 1.2.2 не даёт настроить readonly для отдельной задачи — только глобально. Вместо этого включаем `readonly_dates: !isReadOnly` (было `true` безусловно) глобально, а в `on_date_change` проверяем `task._is_parent`:
- `_is_parent === false` (ролевая задача) → немедленно отменяем визуальное перемещение (тот же паттерн «откатить + `renderGantt`/`refresh`», что уже применяется сегодня для ВСЕХ задач) — эффективно воссоздаёт нынешнее поведение, но только для листовых баров.
- `_is_parent === true` (эпик/стори) → визуальному перемещению не мешаем, но `on_date_change` здесь — НЕ чистый no-op (см. Decision 2 ниже, почему): сохраняем последнюю известную позицию драга в module-level переменную, ничего больше.

Побочный эффект, подтверждённый на бандле: `readonly_dates` — глобальный флаг, поэтому при включении resize-хендлы (левый/правый край бара) отрисовываются на ВСЕХ барах, включая листовые — сам драг всё равно откатывается колбэком, но хендлы визуально видны на ролевых задачах. Осознанный trade-off, а не баг реализации.

Альтернатива — патчить/форкать Frappe Gantt ради per-task readonly — отклонена: непропорционально сложно и хрупко (зависимость от внутренностей чужой библиотеки) ради разницы, которая и так решается на уровне наших же колбэков.

### 2. Определение момента отпускания и reorder по позиции — та же схема, что в модалке, но по X

**Уточнено при реализации**: единого колбэка «на отпускание» в Frappe Gantt 1.2.2 нет (см. Context) — `on_date_change` стреляет многократно во время драга и ненадёжно на `mouseup` (часто без дельты, то есть не стреляет вовсе). Момент отпускания определяем собственным `document`-level слушателем `mouseup`, добавляемым **один раз** при инициализации модуля (`initGanttRenderer`, не при каждом `renderGantt` — иначе воспроизведём ту же утечку слушателей, которую только что убрали в Decision 3 для собственных обработчиков Frappe Gantt):

1. `on_date_change(task, newStart, newEnd)` для `_is_parent === true` — сохраняет `{taskId, newStart, newEnd}` в module-level `pendingParentDrag` (дешёвая операция, без сети/DOM-тяжёлой работы — сохраняет требование Risks о том, что этот колбэк не должен быть тяжёлым).
2. Собственный `document.addEventListener('mouseup', ...)`: если `pendingParentDrag` не пуст — запускает алгоритм reorder (пп. 3-6 ниже) для сохранённой позиции, затем сбрасывает `pendingParentDrag = null` независимо от результата (успех/откат/ошибка).
3. Собрать список «соседей» того же уровня: для эпика — все top-level эпики той же команды; для стори — все стори того же родительского эпика (фильтрация по `_parent_id`/принадлежности, не по визуальной близости — часть соседей может не быть видна в текущем прокрученном диапазоне таймлайна).
4. Отсортировать соседей по их актуальному (бэкендом вычисленному) `_sort_order`.
5. Определить, куда «легла» новая позиция перетащенного бара (`newStart` из `pendingParentDrag`) относительно интервалов соседей — тем же принципом, что и Y-координатный поиск `nextSibling` в модалке (сравнение с серединой соседнего интервала), только по оси X/датам вместо Y/пикселей.
6. Если позиция не пересекла ни одного соседа (осталась в своём исходном промежутке) — это не reorder, откатываем визуально, запрос не шлём (см. спека, сценарий «Перетаскивание отменено без пересечения соседей»).
7. Если пересекла — вычислить новый линейный порядок соседей (тот же алгоритм, что `updateModalInputsOrder`: расставить по позиции, пронумеровать `index + 1`) и отправить `PUT .../reorder` для перетащенного элемента и каждого соседа, чей номер изменился — переиспользуя существующие `apiPut` вызовы, один-в-один как делает `saveOrder()` сегодня.

Почему `document`-level `mouseup`, а не более узкий `$svg`-level: сам Frappe Gantt вешает свой `mouseup`-обработчик на `$svg` внутри `bind_bar_events` — наш слушатель на `document` сработает после его bubbling-фазы (порядок гарантирован, т.к. `mouseup` на SVG всплывает до `document`), и не требует доступа к внутреннему `$svg`-элементу библиотеки. Гейтинг через `pendingParentDrag !== null` защищает от срабатывания на посторонних `mouseup` в остальном приложении (клик по кнопке, закрытие модалки и т.д. — там `pendingParentDrag` всегда пуст).

### 3. Инкрементальное обновление вместо полной пересборки
`renderGantt` перестаёт всегда делать `container.innerHTML='' + new Gantt(...)`. Вместо этого:
- При первом рендере (`ganttChart === null`) или структурном изменении набора задач (другой набор id, не просто другие даты/прогресс/sort_order) — как сейчас, полная пересборка.
- При последующих обновлениях с тем же набором id задач (типичный случай после reorder) — `ganttChart.refresh(ganttTasks)`.
- `applyPostRenderEnhancements` (факт-маркеры, галочки завершения) по-прежнему перевызывается после любого обновления.

**Уточнено при реализации**: `refresh(tasks)` в бандле — это `setup_tasks(tasks)` + `change_view_mode()` без аргументов (сохраняет текущий `view_mode`, доп. сброс не нужен); `$svg`/`$container` не пересоздаются, поэтому document-level обработчики библиотеки (`bind_bar_events`, навешиваемые один раз в конструкторе) не дублируются — попутно устраняет утечку слушателя `document.mouseup`, ранее накапливавшуюся при каждом `new Gantt(...)` на каждое обновление. Побочный эффект, который пришлось скомпенсировать: `refresh()` → `change_view_mode()` → `render()` → `set_scroll_position(options.scroll_to)` — раз `scroll_to` не задан, это сбрасывает `scrollLeft` к началу диапазона дат. Компенсировано вручную: `ganttChart.$container.scrollLeft` сохраняется перед `refresh()` и восстанавливается после.

### 4. Права доступа — используем существующую проверку
`isReadOnly = !userProfile || userProfile.role === 'member'` уже вычисляется в `renderGantt`. И `readonly`, и `readonly_dates` независимо гейтят перемещение бара внутри библиотеки (подтверждено на бандле: обработчик `mousemove` двигает бар только при `!options.readonly && !options.readonly_dates`) — поэтому `readonly_dates: !isReadOnly` (Decision 1) уже достаточно, отдельная проверка в mouseup-слушателе (Decision 2) не обязательна, но не помешает как defense-in-depth.

## Risks / Trade-offs

- **[Риск] `on_date_change` может стрелять очень часто во время драга** (на каждый `mousemove`) — вся логика reorder вынесена из него в отдельный `mouseup`-слушатель (см. Decision 2); сам `on_date_change` для `_is_parent` баров делает только дешёвое сохранение последней позиции в переменную, без сети/тяжёлых вычислений.
- **[Риск] Собственный `document`-level `mouseup`-слушатель должен добавляться один раз**, а не при каждом `renderGantt` — иначе воспроизводим ту же утечку, которую убирает Decision 3 для внутренних обработчиков библиотеки. Митигация: регистрировать в `initGanttRenderer` (вызывается один раз при загрузке модуля), не внутри `renderGantt`.
- **[Риск] Гонка между несколькими PUT-запросами при многошаговом renumbering** (несколько соседей меняют sort_order последовательно, как и в модалке) — если один из промежуточных запросов упадёт, порядок может остаться в противоречивом состоянии. Не хуже текущего поведения модалки (тот же паттерн), отдельно не чиним в рамках этого change.
- **[Риск, найден при реализации] Гонка при быстром повторном драге до завершения предыдущего reorder** — `pendingParentDrag` сбрасывается синхронно перед `await`, поэтому второй драг (другого или того же бара) может запустить `handleParentDragRelease` параллельно первому, ещё не получившему ответ от `apiPut`/`reloadCurrentTeamTasks`. В отличие от риска выше (гонка между шагами ОДНОГО renumbering, унаследованная от модалки, где UI блокируется самой открытой модалкой) — здесь блокирующего UI нет, гонка реалистичнее. **Митигация**: простой in-flight guard — module-level флаг (например, `isParentReorderInFlight`), выставляется перед началом `handleParentDragRelease`, mouseup-слушатель игнорирует новый `pendingParentDrag`, пока флаг не сброшен (в `finally`, после `reloadCurrentTeamTasks`/отката по ошибке). Пользователь, попытавшийся драгнуть второй бар во время выполнения первого reorder, получит визуальный откат второго драга (как будто reorder не состоялся) — приемлемо для первой итерации, не требует UI-индикации "занято".
- **[Trade-off] Вариант A может визуально «дёргаться»** при расхождении между тем, где пользователь отпустил бар, и авторитетной пересчитанной бэкендом позицией — осознанно принято, вариант B (settle-анимация) — следующая итерация при необходимости.

## Migration Plan

Чисто фронтенд, аддитивно — не требует миграций БД, бэкенд не меняется. Деплой обычным образом (без тега, если изменение не попадает в релизный образ отдельно от кода... на самом деле это Go-бинарник, поэтому релизный тег всё равно нужен, т.к. фронтенд раздаётся тем же бэкенд-сервисом, см. `web/gantt/*` — статика встроена в тот же Docker-образ). Отката не требует специальных шагов — предыдущее поведение (модалка) не удаляется.
