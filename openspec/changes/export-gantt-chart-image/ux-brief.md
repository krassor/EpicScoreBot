# UX-постановка для фронтенда (задачи 2.1, 5.1)

Составлена субагентом `ux` (код не пишет). Редакция 1 (задача 2.1) реализована
задачами 3.1–3.9 для отдачи файла браузером. Редакция 2 (эта, задача 5.1)
адаптирует её под доставку ботом в личный чат Telegram (design.md, Решение 1,
«Пересмотрено по результатам проверки в бою») и добавляет обработку кодов
ошибок серверного эндпоинта (design.md Решение 7). Реализуется задачами 6.1–6.2.

## Что изменилось относительно редакции 1

**Остаётся в силе без изменений:**
- Две отдельные кнопки, а не одна с выбором (раздел 1).
- Название форматов «PNG»/«SVG» без слов «растровый»/«векторный» (раздел 2).
- Обе кнопки блокируются на время всей операции, `withSubmitLock` (раздел 3) —
  расширяется на новую фазу «отправка», сам механизм блокировки не меняется.
- Модалка `showErrorModal` как канал для отказов, требующих осознанного
  решения (раздел 4) — раздел переписан по составу отказов, канал тот же.
- Состояние «диаграммы нет» — `disabled` до построения диаграммы (раздел 6).
- Доступность роли `member` (раздел 7).
- Устойчивость раскладки тулбара на ≤480px (раздел 8) — новые подписи не
  меняют видимый текст кнопок, риск раздувания не возникает повторно.
- Сборка SVG/PNG (`buildExportSvg`, легенда, шкала времени) — вне области
  этой постановки, не трогается (задачи 3.1–3.6 неизменны).

**Заменяется:**
- Смысл действия — было «сохранить локально», стало «отправить в чат»:
  `downloadBlob` (`gantt-image-export.js:618-632`) уходит, вместо него —
  `POST /api/gantt/export/image` (задача 6.1). Это меняет `title`/`aria-label`
  кнопок (раздел 1), текст успеха (раздел 5) и полностью — состав и тексты
  отказов (раздел 4), потому что теперь есть сетевой этап со своими кодами
  ошибок вместо только клиентских.
- Индикация хода — было одно состояние «Подготовка», стало два: «Подготовка»
  (сборка/растеризация, как раньше) и «Отправка» (сетевой запрос, новое).
- `showToast('Картинка сохранена', 'success')` (`gantt-image-export.js:108`) —
  текст ложен для новой доставки, заменяется текстом, называющим чат с ботом.

## 1. Подписи кнопок, `title`, `aria-label`

Видимый текст кнопок **не меняется** — `🖼️ PNG` / `📐 SVG`
(`index.html:181-184`) остаётся: смена текста не нужна для передачи смысла
«отправить», а формат должен угадываться мгновенно и в плотном тулбаре
экономия символов важна (раздел 8). Действие уточняется в `title` (десктоп) и
`aria-label` (программы экранного доступа — там короткого «PNG»/«SVG» самого
по себе недостаточно, это только название формата, а не действия).

```html
<button id="btn-export-gantt-png" class="btn btn-secondary btn-sm" type="button" disabled
        title="Отправить в личный чат с ботом — обычная картинка для презентаций и чатов"
        aria-label="Отправить диаграмму в чат с ботом картинкой PNG">🖼️ PNG</button>
<button id="btn-export-gantt-svg" class="btn btn-secondary btn-sm" type="button" disabled
        title="Отправить в личный чат с ботом — можно увеличивать без потери качества, для печати и документов"
        aria-label="Отправить диаграмму в чат с ботом файлом SVG">📐 SVG</button>
```

`aria-label` содержит видимый текст кнопки как подстроку («PNG»/«SVG») —
не нарушает WCAG 2.5.3 (Label in Name). `title` по-прежнему только дополнение
для десктопа, не единственный носитель смысла.

Слова «растровый»/«векторный» по-прежнему не употребляются нигде.

**Приёмка:** видимый текст кнопок не изменился, `id` не изменились; `title` и
`aria-label` обеих кнопок называют действие «отправить в … чат с ботом», а не
«сохранить»; `aria-label` каждой кнопки содержит название своего формата;
раскладка тулбара на ≤480px не меняется.

## 2. Названия форматов

Без изменений относительно редакции 1: иконка + название формата, без
«растровый»/«векторный», иконка не единственный носитель смысла.

## 3. Индикация в две фазы и защита от повторного запуска

Обвязка `runExport`/`withSubmitLock` (`gantt-image-export.js:98-117`)
сохраняется как каркас, но внутри неё теперь две последовательные фазы вместо
одной — готового прецедента на две фазы в проекте нет (`runRegenerateQuarter`,
`app.js:530-565`, — прецедент только для одной), поэтому обе описаны явно.

**Фаза 1 — подготовка** (сборка SVG, для PNG — дополнительно растеризация на
canvas; выполняется целиком на клиенте, сети ещё нет):
- подпись нажатой кнопки — `⏳ Подготовка…` (без изменений).

**Фаза 2 — отправка** (`POST /api/gantt/export/image`, ждём ответ сервера):
- подпись нажатой кнопки меняется на `⏳ Отправка…` непосредственно перед
  вызовом `fetch` — тот же символ `⏳`, что и у фазы подготовки и у
  `runRegenerateQuarter`, чтобы «сейчас идёт процесс» читалось консистентно по
  всему приложению (пункт 7 чек-листа), а различие фаз — в слове, не в иконке.
- если фаза 1 завершилась отказом (клиентский предел — раздел 4) — до фазы 2
  дело не доходит, сеть не используется, кнопка не проходит через «Отправка».

Соседняя (не нажатая) кнопка остаётся заблокированной без смены подписи, как
и раньше.

**Итог и его текст** — раздел 5. **Блокировка снимается в `finally`** на
обеих кнопках независимо от того, на какой фазе и с каким исходом завершилась
операция — без изменений в механике.

**Приёмка:** во время фазы 1 кнопка показывает «⏳ Подготовка…», во время
фазы 2 — «⏳ Отправка…»; при отказе ещё в фазе 1 подпись «⏳ Отправка…» не
появляется (сеть не используется); обе кнопки заблокированы всё время, включая
обе фазы; повторный клик во время любой из фаз не запускает вторую отправку;
подпись восстанавливается и блокировка снимается на любой ветке — успех, отказ
фазы 1, отказ фазы 2.

## 4. Тексты и канал показа для отказов

Разделены по источнику отказа. Все тексты — человеко-понятные, без кода
ошибки и без сырого JSON. Реализация — локальная карта код → {текст, канал} в
`gantt-image-export.js`, ключи — коды из design.md Решения 7; общий
`KNOWN_ERROR_MESSAGES`/`ACTION_REQUIRED_ERRORS` (`utils.js:42-95`) не годится
впрямую — те ключи это строки сообщений конкретных существующих эндпоинтов, а
не коды нового контракта.

Мультипарт-хелпер (задача 6.1) должен переиспользовать `handleHttpError` из
`api.js` тем же способом, что `apiGet`/`apiPost`/`apiPut`/`apiDelete`
(`api.js:18-141`) — тогда 401/403 обрабатываются глобальным оверлеем
одинаково для всех эндпоинтов, а прочие ошибки приходят с уже выставленным
`err.code` (`api.js:59`) — дальнейший разбор ведётся по `err.code`, не по
тексту `message`.

### 4.1. `BOT_CHAT_NOT_STARTED` (409) — канал: `showErrorModal`

Действие устранимо самим пользователем — по конвенции проекта такие отказы
идут в модалку, а не в тост (`ACTION_REQUIRED_ERRORS`).

Кликабельную ссылку дать нельзя: `showErrorModal` экранирует HTML. Текст называет
действие словами и имя бота `@EpicScoreBot` (решение пользователя, см. «Находки
для пользователя»):

> «Чтобы получать файлы, нужно один раз открыть личный чат с ботом
> @EpicScoreBot в Telegram и отправить ему любое сообщение (например,
> «/start»). После этого повторите отправку.»

Один и тот же текст для обоих исходных случаев — `chat_id == 0` (чат ни разу
не открывали) и 403 от Telegram (бот заблокирован): пользователю в обоих
случаях нужно одно и то же действие.

### 4.2. Отказ по пределу холста (клиентский, только PNG, фаза 1) — канал: `showErrorModal`

Не код API — эта проверка (`gantt-image-export.js:142-149`) не доходит до
сети. Текст (обновлён только глагол «сохраните» → «отправьте», причина и оба
выхода — без изменений):

> «Диаграмма в выбранном масштабе слишком велика для PNG — она не помещается
> в допустимый размер холста браузера. Выберите более крупный масштаб времени
> (например, «Неделя» или «Месяц») либо отправьте диаграмму в формате SVG —
> на него это ограничение не действует.»

### 4.3. `FILE_TOO_LARGE` (413) и клиентская проверка 50 МБ перед отправкой — канал: `showErrorModal`

Другая причина, чем 4.2, — не пиксели холста, а лимит Bot API на размер
файла (design.md Решение 7: 50 МБ), относится к обоим форматам. Нужен
отдельный текст, иначе пользователь применит не тот совет; переключение
формата здесь не гарантирует результат, поэтому такой альтернативы текст не
предлагает:

> «Подготовленный файл получился больше 50 МБ — так много Telegram не
> позволяет боту отправить. Выберите более крупный масштаб времени
> (например, «Неделя» или «Месяц»), чтобы уменьшить размер файла, и
> попробуйте снова.»

Клиентская проверка (задача 6.1) и серверный `FILE_TOO_LARGE` показывают этот
же текст этим же каналом — для пользователя это одна ситуация, пойманная в
разных точках (клиент — до фазы «Отправка», сервер — страховка).

### 4.4. `TELEGRAM_SEND_FAILED` (502) — канал: `showToast(..., 'error')`

Не требует решения пользователя, только повтора. Текст отличается от текста
ошибки сборки (4.7), чтобы по формулировке было понятно, на какой фазе случился
отказ:

> «Не удалось отправить картинку в чат. Попробуйте ещё раз.»

### 4.5. `NOTIFIER_UNAVAILABLE` (500) — канал: `showToast(..., 'error')`

Бот не поднят на сервере — «подождите и повторите», поэтому тост. Собственный
текст, потому что «попробуйте ещё раз» здесь вводит в заблуждение:

> «Бот временно недоступен, отправка невозможна. Попробуйте позже.»

### 4.6. `INVALID_FORMAT` / `INVALID_FILE` (400) — канал: `showToast(..., 'error')`

При штатной работе интерфейса не должны происходить — клиент сам собирает
файл и сам передаёт `format`. Пользователю нечего чинить; технических деталей
не показываем:

> «Не удалось отправить картинку. Попробуйте ещё раз или обновите страницу.»

Тот же текст и канал — для сетевого сбоя без `err.code` (offline, обрыв
соединения) и любого не перечисленного явно кода: это общий пол для
непредвиденного, а не подмена конкретных случаев 4.1–4.5.

### 4.7. Ошибка сборки (фаза 1, без сети) — без изменений

`showToast('Не удалось подготовить картинку. Попробуйте ещё раз.', 'error')`
(`gantt-image-export.js:112`) остаётся как есть.

**Приёмка:** каждый код из таблицы design.md Решения 7 даёт свой текст без
слов «код», «error», без JSON; `BOT_CHAT_NOT_STARTED` и отказы по размеру
(4.2, 4.3) показываются `showErrorModal`; `TELEGRAM_SEND_FAILED`,
`NOTIFIER_UNAVAILABLE`, `INVALID_FORMAT`/`INVALID_FILE` и сетевой сбой без
кода — тостом; тексты 4.2 и 4.3 не совпадают; ни один из этих путей не
показывает тост об успехе.

## 5. Текст успеха

Заменяет `showToast('Картинка сохранена', 'success')`
(`gantt-image-export.js:108`) — текст должен называть, где искать файл:

> `showToast('Файл отправлен в чат с ботом', 'success')`

Показывается только после `200 {"status":"sent"}` от сервера. Клиентские
отказы (предел холста 4.2 и проверка 50 МБ 4.3) по-прежнему не показывают тост
успеха — правило `gantt-image-export.js:104-109` сохраняется и расширяется на
оба клиентских отказа.

**Приёмка:** сообщение об успехе называет чат с ботом, не «загрузки»; успех
показывается строго после `200` от сервера; ни один из отказов раздела 4 не
приводит к показу этого сообщения.

## Находки для пользователя

**Фронтенду не известно имя бота — кликабельную ссылку на чат в
`BOT_CHAT_NOT_STARTED` дать нельзя без изменения API.** `GET /api/gantt/profile`
отдаёт данные пользователя, но не бота; во фронтенде нет ни имени бота, ни
`t.me/`-ссылки на него (`t.me/${username}` в `scoring-panel.js:977` ведёт на
другого пользователя); `Telegram.WebApp` используется только для `initData` и
`expand()`. Поэтому текст 4.1 называет действие словами. Кликабельная ссылка
потребовала бы отдавать имя бота с сервера — это изменение контракта, вынесено
на решение пользователя.

**Решение пользователя:** имя бота — `@EpicScoreBot`, вписывается в текст 4.1
напрямую, без изменения API.
