# UX-постановка для фронтенда (задача 2.1)

Составлена субагентом `ux` (код не пишет). Реализуется задачами 3.1–3.9.

## Находки, определившие решения

**Тост непригоден как индикатор хода подготовки.** `showToast` (`utils.js:3-34`) сам
скрывается через 4000 мс. Подготовка большой картинки может идти дольше — индикатор
исчезнет, и пользователь решит, что операция оборвалась. Нужен индикатор, живущий ровно
столько, сколько идёт работа.

**Готовый паттерн для этого уже есть.** `runRegenerateQuarter` (`app.js:530-565`) решает ту
же задачу для операции сопоставимой длительности: `withSubmitLock` блокирует кнопку,
`btn.innerHTML` меняется на «⏳ Перегенерация...», в `finally` подпись возвращается,
`showToast` сообщает итог. Переиспользовать один в один.

**`title` не работает на основном клиенте.** В мобильном Telegram WebApp наведения мышью
нет, подсказка не откроется. Разница форматов должна читаться в самой подписи кнопки, а не
только по hover.

**`.toolbar-right` на ≤480px уже плотный.** Там `.view-modes` и `#task-count`, причём
`.view-modes`/`.btn-view` получили `flex: 1` специально под этот контейнер
(`responsive.css:365-378`), а `flex-wrap` унаследован от базового правила. Две новые кнопки
без явного управления переносом либо ужмут переключатель масштаба, либо дадут рваную
раскладку — тот же класс дефекта, что чинила `stabilize-control-widths`.

**Для отказа есть готовый канал.** `showErrorModal` / `ACTION_REQUIRED_ERRORS`
(`utils.js:69-133`) уже показывает ошибки, требующие осознанного решения. Отказ по пределу
холста структурно такой же — нужен выбор пользователя, а не «повторить».

Пунктов, требующих решения пользователя, нет: всё перечисленное — размещение, подпись,
обратная связь и доступность, без изменения логики.

## 1. Две кнопки, а не одна с выбором

На вкладке «Отчёты» уже есть прямой прецедент двух форматов —
`btn-export-report-pdf` / `btn-export-report-xlsx` (`index.html:515-518`), обе
`.btn.btn-secondary.btn-sm`, каждая в один клик. Выпадающих меню в проекте нет ни одного;
вводить новый UI-примитив ради экономии одной кнопки не стоит — два явных действия быстрее
и не требуют фокус-ловушки.

**Место** — `.toolbar-right` вкладки «Гант» (`index.html:181-185`), после `#task-count`. Не
в `.toolbar-left`: там действия, доступные только `leader`/`admin`, а `.toolbar-right` уже
зона «вид и статус», доступная всем ролям.

```html
<div class="gantt-export-actions">
    <button id="btn-export-gantt-png" class="btn btn-secondary btn-sm" type="button" disabled
            title="Обычная картинка — для презентаций, документов и чатов">🖼️ PNG</button>
    <button id="btn-export-gantt-svg" class="btn btn-secondary btn-sm" type="button" disabled
            title="Можно увеличивать без потери качества — для печати и вставки в другие документы">📐 SVG</button>
</div>
```

`.gantt-export-actions` нужен только для управления переносом (раздел 7):
`display: flex; gap: var(--space-2); align-items: center`. Стили `.btn`/`.btn-secondary`/
`.btn-sm` не дублировать — они уже есть в `components.css:344-410`.

**Приёмка:** две отдельные кнопки, по стилю идентичные кнопкам экспорта отчёта; клик по
каждой запускает подготовку своего формата без промежуточного меню.

## 2. Названия форматов

Подписи: `🖼️ PNG` и `📐 SVG`. Разные пиктограммы — дополнительный визуальный якорь в плотном
тулбаре, но основной различитель всегда текстовый; иконка никогда не единственный носитель
смысла.

`title` как дополнение для десктопа:
- PNG — «Обычная картинка — для презентаций, документов и чатов»
- SVG — «Можно увеличивать без потери качества — для печати и вставки в другие документы»

Слова «растровый» и «векторный» не употреблять нигде — ни в подписи, ни в `title`, ни в
текстах обратной связи. На мобильном пользователь ориентируется по названию формата (PNG и
SVG — общеизвестные обозначения, как PDF и Excel в прецеденте отчётов) плюс по иконке.

**Приёмка:** ни в одной видимой пользователю строке нет слов «растровый»/«векторный»;
подписи кнопок различаются и иконкой, и названием формата.

## 3. Ход подготовки и защита от повторного запуска

Переиспользовать паттерн `runRegenerateQuarter` (`app.js:530-565`) один в один.

- **Блокируются обе кнопки сразу**, независимо от нажатой: они делят один основной поток
  сериализации (design.md Решение 4 — источник один), и запускать вторую подготовку во время
  первой так же бессмысленно, как кликать повторно по той же. `withSubmitLock` уже принимает
  массив (`utils.js:163-184`), новый код в `utils.js` не нужен.
- **У нажатой кнопки подпись меняется** на `⏳ Подготовка…`, в `finally` восстанавливается.
  Соседняя остаётся заблокированной без смены подписи — выключенный вид уже сообщает
  «сейчас недоступно».
- **Итог** — `showToast('Картинка сохранена', 'success')`. Тост здесь уместен: это
  подтверждение свершившегося, а не индикатор процесса.
- **Непредвиденная ошибка** (не превышение предела) — `showToast('Не удалось подготовить
  картинку. Попробуйте ещё раз.', 'error')`, без деталей исключения.

**Приёмка:** во время подготовки обе кнопки `disabled`; повторный клик не запускает вторую
подготовку; блокировка снимается на обеих и на ветке ошибки; подпись нажатой кнопки в
процессе отличается от состояния покоя.

## 4. Отказ при превышении предела растрового формата

Использовать существующий `showErrorModal(text, initiator)` (`utils.js:99-133`) — тот же
канал, что показывает ошибки, требующие осознанного решения. Это клиентская, не API-ошибка,
поэтому вызывать напрямую с готовым текстом, а не через `handleApiError`.

Текст можно скорректировать, но три смысловых блока обязательны — причина, первый выход,
второй выход:

> «Диаграмма в выбранном масштабе слишком велика для PNG — она не помещается в допустимый
> размер файла. Выберите более крупный масштаб времени (например, «Неделя» или «Месяц») либо
> сохраните диаграмму в SVG — для него это ограничение не действует.»

Модалка использует существующую разметку `#modal-error`, новый компонент не создаётся.
Стандартный заголовок «Не удалось выполнить действие» переопределять не нужно.

Проверка предела выполняется **до** растеризации (задача 3.6) и относится только к PNG —
кнопка SVG в этот момент активна и работает штатно.

**Приёмка:** при превышении предела PNG-файл не создаётся; пользователь видит модалку с
причиной и обоими выходами; кнопка SVG в этот момент кликабельна и доводит сохранение до
успеха на той же диаграмме.

## 5. Состояние «диаграммы нет»

Обе кнопки изначально несут `disabled` в разметке, как `btn-export-report-*`.

Источник истины для включения — тот же сигнал, что уже переключает `#gantt-empty`/
`#gantt-chart` и обновляет `#task-count`: блок в `renderGantt(tasks)`
(`gantt-renderer.js:290-307`). Рядом с `taskCount.textContent` добавить
`btnExportPng.disabled = btnExportSvg.disabled = tasks.length === 0`.

Это единая точка, покрывающая оба случая из спеки — «команда не выбрана» и «команда выбрана,
задачи не сгенерированы»: если диаграммы нет, `tasks` пуст независимо от причины. Отдельного
текста у кнопок не нужно — причина уже объяснена крупным блоком `#gantt-empty`, а в проекте
отключённые `epicSelect`/`btnGenerate` тоже не сопровождаются пояснением у самого элемента.

**Приёмка:** до выбора команды и при команде без задач обе кнопки недоступны; как только
`tasks.length > 0` — доступны без перезагрузки.

## 6. Доступность роли `member`

Кнопки экспорта **не** добавлять в список, который скрывается для `member` через
`btn.style.display` (`app.js:112-123`). Они видимы и доступны всем ролям, единственное
условие — наличие диаграммы.

Рядом с местом, где выставляется роль-специфичная видимость (`app.js:109-123`), добавить
комментарий, объясняющий асимметрию:

```js
// Кнопки экспорта картинки (btn-export-gantt-png/svg) сюда сознательно не входят:
// сохранение картинки не меняет ни данные, ни расписание, в отличие от генерации/
// перегенерации/переупорядочивания выше — ограничивать его по роли нет причины
// (export-gantt-chart-image, «Сохранение доступно всем, кто видит диаграмму»).
```

**Приёмка:** под `member` при построенной диаграмме обе кнопки видимы и кликабельны,
поведение идентично `leader`/`admin`.

## 7. Устойчивость раскладки тулбара

Подписи кнопок статичны и от данных не зависят, поэтому раздувания от содержимого нет. Риск
другой: две кнопки конкурируют за место в уже плотном `.toolbar-right` на узких экранах.

В `responsive.css`, в блок `@media (max-width: 480px)` рядом с существующими правилами
`.toolbar-right`/`.view-modes`/`.btn-view` (`:365-378`):

```css
.gantt-export-actions {
    flex-basis: 100%;
    justify-content: flex-end;
}
```

Кнопки уходят на отдельную строку внутри `.toolbar-right` вместо того, чтобы ужимать
переключатель масштаба — тот же приём «явно зафиксировать перенос», что уже применён к
`.toolbar-row-settings` и модификаторам `.select--*`. На ширинах больше 480px ничего не
меняется.

**Приёмка:** на ≤480px кнопки не сжимают `.view-modes` и не обрезают подписи
«День»/«Неделя»/«Месяц», уходя на отдельную строку; на 481–1024px и шире остаются в общей
строке без горизонтального скролла страницы.

## Не трогать

- Обработчики и id `btn-generate`, `btn-regenerate-quarter`, `btn-reorder-epics`,
  `btn-reorder-stories`, `#task-count`, `.view-modes`/`.btn-view`.
- Разметку и стили `.gantt-legend` (`index.html:186-200`) — на экране легенда остаётся как
  есть; её воспроизведение внутри экспортируемого SVG нативными фигурами — отдельная задача
  3.3, к этой постановке не относится.
- Сигнатуры `showErrorModal`/`showToast`/`withSubmitLock` — использовать как есть.
- Кнопки экспорта отчёта и логику `reports-panel.js`.
