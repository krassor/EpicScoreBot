## Context

Мотивация — см. `proposal.md` («Why»). Здесь только то состояние кода, которое определяет подход.

Сессия веб-интерфейса создаётся в двух местах и оба кладут в `UserSession.TelegramID` **числовой** Telegram user ID:

- `handlers/gantt.go:1224` (`TelegramAuth`, Login Widget) — `query.Get("id")`;
- `middleware/telegram_auth.go:175` (`VerifyTelegramWebAppData`, Mini App) — `strconv.FormatInt(tpUser.ID, 10)`.

Сессия подписывается HMAC и кладётся в cookie `tg_sys_auth` на 7 дней; в ней уже есть отдельное поле `Username`.

Справочник `users` ключуется по **@username**: так его заполняет бот (`telegram/handlers_admin.go:72` — `strings.TrimPrefix(args[0], "@")`, `telegram/handlers_session.go:109`), так же ищет (`telegram/handlers.go:98`, `handlers_epic.go:155`), и так же трактует фронтенд (`scoring-panel.js:975` срезает ведущий `@`, значит в данных встречаются оба написания — пакетный импорт `@` не срезает).

`session.TelegramID` уходит ключом справочника в 41 место HTTP-слоя: `FindUserByTelegramID`, `GetTeamsByUserTelegramID` и адаптер `repositories.TeamAdminAuth` (`IsTeamAdminOfAny`, `IsTeamAdminOf`, `AdminTeamIDs`, все три резолвят пользователя через `FindUserByTelegramID`). Ни одно из них не находит совпадения. Отказы при этом тихие: `TeamAdminAuth` по договорённости гасит ошибку резолвинга в «не администратор», `RoleAuth` превращает её в 403. Поэтому рассинхрон виден только там, где отказ доходит до пользователя явно, — в экспорте картинки.

Конфигурационный superadmin сверяется по `session.Username` и БД не касается — этим и объясняется, что веб-панель у superadmin работает.

## Goals / Non-Goals

**Goals:**

- Один ключ опознания сессии в справочнике, вычисляемый ровно в одном месте, — чтобы рассинхрон не мог возникнуть снова через новый вызов.
- Доставка картинки вообще перестаёт зависеть от справочника.
- Ранее выданные cookie продолжают работать без перелогина.

**Non-Goals:**

- Перевод справочника на числовой Telegram ID (`users.telegram_id` остаётся @username) — см. «Дальнейшие шаги».
- Изменение формата ошибок API и приведение `writeError` к `writeErrorCode` в middleware — отдельное архитектурное решение, здесь не делается.
- Изменение способа сборки картинки на клиенте и контракта `POST /api/gantt/export/image` — не трогаем.
- Восстановление `users.chat_id` для рассылки напоминаний (`notify.go`) — отдельная задача.

## Decisions

### Решение 1. Адресат картинки — числовой ID из сессии, без обращения к БД

`ExportGanttImage` берёт `session.TelegramID`, разбирает его `strconv.ParseInt` и передаёт как `chatID` в `docSender.SendDocumentToChat`. Обращение `FindUserByTelegramID` и проверка `user.ChatID == 0` удаляются.

Основание: в Telegram ID личного чата с пользователем равен ID самого пользователя, поэтому промежуточное звено «справочник → `users.chat_id`» не даёт ничего, кроме двух дополнительных условий отказа. Свойство, ради которого писалась проверка, сохраняется в полном объёме: адресат по-прежнему берётся только из подписанной сессии, никогда из тела запроса.

Единственным источником `BOT_CHAT_NOT_STARTED` остаётся `bot.ErrorForbidden` (403 от Telegram) — ровно то состояние, которое подсказка «откройте чат» и описывает.

Если `session.TelegramID` не разбирается как число (такого быть не должно: оба пути создания сессии кладут туда число), — 500 `internal_error` с записью в лог, а не `BOT_CHAT_NOT_STARTED`: это сбой сервера, и подсказка «откройте чат» снова назвала бы неверную причину. Тот же приём, что уже применён в обработчике для ошибок БД.

*Альтернатива:* чинить резолвинг и продолжать слать на `users.chat_id`. Отвергнута: требует, чтобы пользователь был и заведён в справочнике, и хотя бы раз написал боту (иначе `chat_id = 0`), — два условия вместо нуля, и оба дают отказ там, где Telegram отправил бы файл.

### Решение 2. Ключ справочника вычисляется один раз — в `UserSession`

`middleware.UserSession` получает метод `DirectoryKey() string`: нормализованный `Username` — `strings.ToLower(strings.TrimPrefix(strings.TrimSpace(s.Username), "@"))`, пустая строка, если username не задан. Поле `TelegramID` сохраняет прежний смысл (числовой ID) и прежнее имя — его читает `Решение 1` и отдаёт `GetProfile`.

Все обращения HTTP-слоя к справочнику переходят с `session.TelegramID` на `session.DirectoryKey()`. Сигнатуры `Repository.FindUserByTelegramID`, `GetTeamsByUserTelegramID` и `TeamAdminAuth` не меняются — меняется только то, что в них передают.

*Альтернатива А:* положить username прямо в `UserSession.TelegramID`. Отвергнута: call-sites не пришлось бы трогать, но поле с именем `telegram_id`, содержащее username, — та же путаница, что и породила баг, плюс `Решение 1` потеряло бы числовой ID, плюс cookie, выданные до релиза, содержали бы в этом поле число и молча резолвились бы в никуда.

*Альтернатива Б:* новое поле `DirectoryKey` в сериализуемой структуре сессии. Отвергнута: значение выводится из `Username`, хранить его отдельно — значит получить ещё одну пару полей, способных разойтись, и зависеть от того, какой версией кода выписан cookie. Метод считает его на лету из уже имеющегося поля, поэтому старые cookie работают сразу.

### Решение 3. Сравнение в БД нормализуется на стороне запроса

В `FindUserByTelegramID` и `GetTeamsByUserTelegramID` условие становится `WHERE lower(ltrim(u.telegram_id, '@')) = $1` (параметр приходит уже нормализованным из `DirectoryKey`). Данные не мигрируются: в `users.telegram_id` остаётся то, что туда занесли.

Основание: справочник заполнялся разными путями и содержит оба написания; нормализация на чтении чинит все записи разом, не трогая данные и не требуя миграции. Индекс по выражению не добавляется — таблица `users` в масштабе продукта (участники нескольких команд) исчисляется десятками строк, seq scan по ней дешевле сопровождения миграции.

*Альтернатива:* разовая миграция `UPDATE users SET telegram_id = lower(ltrim(telegram_id,'@'))`. Отвергнута в рамках этой заявки: пользователь выбрал вариант без миграции, к тому же бот продолжает записывать username в исходном регистре, так что нормализация на чтении нужна в любом случае.

### Решение 4. Отказ различает «не зарегистрирован» и «нет @username»

`RoleAuth` и `GetProfile` перед обращением к справочнику проверяют `DirectoryKey() == ""`. Пустой ключ означает, что у пользователя не задан @username, и отказ сопровождается именно этим объяснением — тем же по смыслу, что уже выдаёт бот («❌ У вас не задан @username в Telegram», `telegram/handlers_epic.go:150`).

Статус в обоих случаях остаётся 403 — меняется только текст. Формат ответа в middleware (`{"error":"..."}`) не трогаем; `GetProfile` переводится на `writeErrorCode` со структурными кодами `USERNAME_REQUIRED` и `USER_NOT_REGISTERED`, поскольку именно его ответ разбирает фронтенд.

Фронтенд: `denied-overlay` (`index.html:51`) сейчас показывает фиксированный текст. Первый `<p>` получает `id` и заполняется сообщением из ответа, когда оно пришло; при отсутствии — прежний текст. `api.js` в ветке 403 передаёт `errData` дальше, а не теряет его (сейчас на этом пути бросается `FORBIDDEN` без сообщения).

### Решение 5. Порядок проверки роли не меняется

Последовательность `superadmin (конфиг, по Username) → team-admin (БД) → member (БД)` в `RoleAuth` и `GetProfile` сохраняется как есть. Меняется только ключ, которым выполняются два последних шага. Это сознательно узкая правка: поведение прав описано спекой `team-admin`, и заявка чинит его исполнение, а не пересматривает.

## Risks / Trade-offs

- **Пользователи, работавшие до сих пор как superadmin, впервые получат реальные роли `admin`/`member`, и веб-панель у них изменится.** → Это и есть починка: права начинают соответствовать спеке `team-admin`. Superadmin из конфигурации не затронут. Проверить на проде после деплоя хотя бы одним участником и одним team-admin (задача 5.2).
- **Смена @username в Telegram обрывает опознание — человек перестаёт быть собой для системы.** → Уже действующее поведение бота, заявка его не ухудшает. Лечится правкой записи администратором; устойчивое решение вынесено в «Дальнейшие шаги».
- **Участник без @username потеряет доступ к вебу.** → Он и сейчас его не имеет (403 без объяснения) и не может пользоваться ботом. Заявка добавляет внятное объяснение и действие, которое это чинит.
- **Экспорт перестаёт быть «только для заведённых в справочнике»: файл сможет получить любой, кто прошёл `TelegramAuth`.** → Приемлемо и не ново: роут и раньше стоял без `RoleAuth`, а худшее достижимое действие — отправить себе же собранную у себя же картинку. Проверка сигнатуры файла и лимит 50 МБ остаются.
- **`lower(ltrim(...))` отключает использование индекса по `telegram_id`.** → На таблице в десятки строк несущественно; при росте — выражение-индекс отдельной миграцией.
- **41 механическая замена в 11 файлах — риск пропустить вызов.** → Проверяется `grep -rn "session.TelegramID" internal/ | grep -v _test`: после правки остаются только `== ""` и `Решение 1` в `gantt_export.go` плюс отдача профиля (задача 4.3).

## Migration Plan

Миграций БД нет, данные не меняются, изменений конфигурации нет — обычный деплой по тегу (`/deploy`).

Откат: обратный деплой предыдущего образа. Состояния, которое нужно было бы откатывать отдельно, заявка не создаёт — cookie совместимы в обе стороны (оба поля в них уже есть и там, и там).

## Дальнейшие шаги (вне объёма)

- Перевод справочника на числовой Telegram ID как канонический ключ (`users.tg_user_id`), устойчивый к смене @username; @username остаётся отображаемым.
- Заполнение `users.chat_id` в момент успешной веб-авторизации или успешной отправки документа — сейчас он заполняется только когда пользователь пишет боту, из-за чего часть напоминаний (`notify.go`) не доходит.
- Приведение ответов middleware к общему формату `{ "error": { "code", "message" } }`.
