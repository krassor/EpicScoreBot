## Why

На реальных данных пользователь наблюдал явно некорректное расписание после reorder эпиков: эпик с `sort_order=1` (CREDCARD-12446) получил самые ПОЗДНИЕ даты (июль-октябрь) вместо самых ранних, а два других эпика (`sort_order=2` и `3`) получили пересекающиеся по датам роли — при том что все задействованные ролевые задачи были со `progress=0`, без зафиксированного факта и без ручного смещения (`start_offset_days=0`).

Проведено расследование (временный воспроизводящий тест на реальном коде `RecalculateTeamSchedule`/`recalculateEpicSchedule`, 4 сценария, включая точное воспроизведение всех 6 эпиков команды и последовательности `PUT /epics/{id}/reorder`, которую отправляет фронтенд): сам алгоритм пересчёта расписания **корректен и детерминированно самокорректируется** при каждом чистом (изолированном) вызове — баг не воспроизвёлся ни в одном сценарии. Исключены как причина: некорректный порядок эпиков в запросе к БД, привязка `gantt_tasks.epic_id` для стори, группировка параллельных ролей, влияние порядка генерации задач.

Единственная оставшаяся, архитектурно подтверждённая (не гипотетическая) находка: вокруг `RecalculateTeamSchedule` (`internal/gantt/ganttService.go`) **нет ни транзакции, ни блокировки** — это цепочка независимых `SELECT`/`UPDATE` без изоляции. `ReorderEpic`/`ReorderStory` каждый вызывают полный пересчёт расписания команды. Если два таких вызова для одной команды выполнятся почти одновременно (что стало более вероятно после недавнего добавления drag-reorder прямо на графике, работающего параллельно с уже существующей модалкой «Порядок…» — оба пути дёргают один и тот же пересчёт), их промежуточные чтения/записи (`roleFreeAt`, `teamFloor`, обновление дат по одной задаче за раз) могут переплестись и оставить именно такую несогласованную картину.

**Честно фиксируем уровень уверенности**: это наиболее вероятная из оставшихся причин, но не доказана логами реального инцидента (доступа к прод-логам нет). Учитывая, что сам алгоритм самокорректируется «с нуля» при каждом чистом вызове (см. комментарий в коде: `RecalculateTeamSchedule`, "self-corrects instead"), после добавления блокировки достаточно одного чистого пересчёта, чтобы исправить уже накопившееся неверное расписание — отдельная миграция данных не требуется.

## What Changes

- Вызовы `RecalculateTeamSchedule` для одной и той же команды сериализуются — конкурентный вызов ждёт завершения предыдущего, а не выполняется параллельно с ним.
- Механизм — in-process блокировка на уровне `Service` (per-team мьютекс), без новых зависимостей и без изменения `Repository`-интерфейса. Обоснование выбора (vs блокировка на уровне БД) — в design.md.
- Добавляется логирование начала/окончания `RecalculateTeamSchedule` и факта ожидания на блокировке — чтобы при повторном возникновении проблемы (если гипотеза окажется неполной) в логах было видно, была ли конкуренция за пересчёт данной команды.
- **Не входит в скоуп**: миграция/ручное исправление уже накопленных на проде некорректных дат — согласно анализу, они самоисправятся при следующем корректном (изолированном) вызове пересчёта после деплоя; ручной шаг — просто ещё раз сохранить любой reorder для этой команды после деплоя фикса (зафиксировано в tasks.md как проверка, не код).
- **BREAKING**: нет.

## Capabilities

### New Capabilities
- `gantt-schedule-recalc-locking`: пересчёт расписания команды (`RecalculateTeamSchedule`) выполняется не более одного раза одновременно для одной команды — конкурентные запросы сериализуются.

### Modified Capabilities
(нет)

## Impact

- **Backend only** — `internal/gantt/ganttService.go` (`Service`, `RecalculateTeamSchedule`). `ReorderEpic`/`ReorderStory`/`ReorderTask`/генерация задач и другие вызывающие не меняются по сигнатуре.
- Зависимостей не добавляется — используется стандартный `sync.Mutex`/аналог из stdlib.
- Ограничение выбранного подхода: in-process блокировка защищает только в рамках ОДНОГО инстанса бэкенда. Если проект когда-либо перейдёт на несколько реплик бэкенда за балансировщиком — потребуется переход на блокировку на уровне БД (Postgres advisory lock). Сейчас деплой — один контейнер (`docker-compose`, см. `devops.md`), поэтому in-process блокировки достаточно.
- **QA**: после деплоя — вручную выполнить ещё один (любой) reorder для команды пользователя и убедиться, что расписание стало консистентным (эпик 1 — самые ранние даты, роли соседних эпиков не пересекаются). Логи проверить на наличие "ожидание блокировки" — если оно происходит регулярно, гипотеза подтверждается практикой.
