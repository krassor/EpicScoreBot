## 2. Frontend

- [x] 2.1 Сверить текущее состояние `web/gantt/css/components.css`, `gantt.css`, `responsive.css` и `index.html` с задачами заявки `improve-web-ux` (design.md Решение 6): она правит те же правила, весь её код выкачен, но она не заархивирована и ведётся из другой сессии. Проверка: зафиксировано, какие правила уже изменены ею, чтобы правки не затёрли друг друга.
- [x] 2.2 Ограничить рост шести списков в строчных контейнерах тремя классами-модификаторами по ролям (`ux-brief.md`, раздел 1). Базовое правило `.select` (`components.css:136-144`) **не менять**: девять списков в формах и модалках уже стабильны за счёт `align-items: stretch` в колоночных контейнерах, и общий `max-width` их бы сломал (design.md Решения 1–2, исправленные после UX-ревью). Проверка: список эпиков сохраняет ширину при квартале с длинными названиями, при пустом списке и при коротких названиях; список кварталов не становится неоправданно широким.
- [x] 2.3 Реализовать усечение непомещающегося значения с признаком усечения и доступом к полному тексту (design.md Решение 3). **Проверить фактически в целевом окружении** (Chromium мобильный в Telegram WebApp и десктопный Chrome), что усечение выбранного значения в нативном `<select>` действительно работает — браузеры реализуют это по-разному. Если без замены `<select>` на собственный компонент усечение недостижимо, **остановиться и вынести вопрос пользователю**, не подменяя требование. Проверка: длинное название усечено с признаком, ширина не изменилась, полное название доступно; короткое значение не усекается.
- [x] 2.4 Стабилизировать счётчик `#task-count` и бейджи роли (design.md Решение 4): резервирование места под ожидаемый диапазон значений плюс выравнивание ширины цифр. Проверка: смена числа задач с однозначного на трёхзначное не смещает соседние элементы; смена роли на более длинную не перекладывает шапку.
- [x] 2.5 Ограничить ширину имени пользователя `#user-name` в шапке с усечением. Проверка: длинное имя не сдвигает выбор команды, бейдж роли и кнопку выхода.
- [x] 2.6 Добавить `max-width: none` для новых модификаторов в мобильные медиа-блоки (`responsive.css:75-77` и блок тулбара): иначе `max-width` окажется сильнее правил `width: 100%`, намеренно растягивающих эти элементы, и вместо полной ширины ряда получится узкий блок с пустотой сбоку. Заодно проверить сетки модалок (`components.css:394-405`) и остальные адаптивные ветки (`responsive.css:154-190`). При конфликте снимать предел точечно в этих контекстах, а не ослаблять общее правило (design.md, Risks). Проверка: модалки эпика, истории и риска выглядят как раньше; на узких экранах элементы по-прежнему растягиваются на всю ширину ряда.
- [x] 2.7 Реализовать остальные находки UX-постановки из 1.1, относящиеся к подаче. Проверка: соответствует критериям приёмки постановки.
- [x] 2.8 Вернуть усечение на узких экранах. Правило `.toolbar-row > * { white-space: normal }` (`responsive.css:186`, из заявки `improve-web-ux`; такое же есть у `.toolbar-left > *` на `:172`) перебивает `nowrap` у модификаторов, поэтому на `≤768px` длинное название эпика не усекается, а переносится на несколько строк: ширина стабильна, но плавает высота — «та же проблема в другой оси» (design.md Решение 3). Поведение не новое, но и не починенное, а Telegram WebApp почти всегда мобильный, то есть это основной сценарий. Вернуть `white-space: nowrap` трём модификаторам точечно внутри мобильного блока, не трогая общее правило тулбара. Добавленный объём сверх исходного плана — согласован с пользователем. Проверка: на `≤768px` длинное название эпика усечено многоточием в одну строку, высота списка не зависит от длины названия, элемент по-прежнему растянут на всю ширину ряда.

## 3. QA — ручная проверка

Автотестов в этой заявке нет: JS-раннера в проекте не существует (см. design.md, Risks). Все проверки ниже — ручные, по сценариям `specs/web-stable-control-layout/spec.md`, и каждую нужно пройти **на данных обоих крайних случаев** — с короткими и с заведомо длинными названиями.

- [ ] 3.1 Пройти сценарии требования «Ширина выпадающего списка не зависит от его содержимого»: квартал с длинными названиями эпиков, пустой квартал, а также списки на экранах скоринга, отчётов и админ-панели. Проверка: ширина каждого списка одинакова во всех состояниях данных.
- [ ] 3.2 Пройти сценарии требования «Непомещающееся значение усекается с сохранением доступа к полному тексту» в обоих целевых браузерах. Проверка: усечение видно, ширина стабильна, полное значение доступно; короткое значение не усекается.
- [ ] 3.3 Пройти сценарии требований по счётчику, бейджу роли и имени пользователя. Проверка: соседние элементы не смещаются ни в одном из случаев.
- [ ] 3.4 Пройти сценарии требования «Панель инструментов сохраняет раскладку при смене данных»: переключение квартала с заполненного на пустой и обратно, смена команды, состояние во время загрузки и после неё. Проверка: кнопки остаются на тех же местах, по завершении загрузки элементы не перепрыгивают.
- [ ] 3.5 Пройти сценарий требования «Устойчивость раскладки сохраняется на узких экранах»: мобильное разрешение, команды с длинными и короткими названиями эпиков. Проверка: число рядов панели и порядок элементов одинаковы в обоих случаях.
